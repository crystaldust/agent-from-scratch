# 01. Agent Loop —— Message 格式详解

> 写 agent loop 时，逻辑本身只有十几行：**调模型 → 把回复追加进 messages → 执行工具 → 把结果追加进 messages → 再调模型**。
> 真正容易出错的是 messages 里每一条消息、每一个 block 的**结构和字段名**。字段名错一个字母、类型错一层（string vs list vs dict），API 就会报 400，或者本地 `json.dumps` 直接失败。
>
> 本文以本项目使用的 **Anthropic Messages API**（`anthropic` SDK 2.3.0，`client.messages.create`）为主线，
> 再对照讲解 **OpenAI Chat Completions** 和 **OpenAI Responses API** 两种同样流行的格式，最后给出常见坑和检查清单。

## 1. 心智模型：messages 是一份只追加的对话日志

大模型 API 是**无状态**的：服务端不记得上一轮说过什么。每次调用都要把完整历史重新发过去。所以：

```
messages = [
  user:       "帮我看看当前目录有什么文件"          ← 人类输入
  assistant:  [text, tool_use(bash: ls)]           ← 模型决定调用工具
  user:       [tool_result(ls 的输出)]              ← 你的程序执行工具后回填
  assistant:  [text: "当前目录有 3 个文件..."]      ← 模型基于结果给出回答
]
```

几个关键认知：

| 认知 | 说明 |
|---|---|
| **工具结果是 user 发的** | 在 Anthropic 格式里，没有单独的 `tool` 角色，工具执行结果放在 `role: "user"` 消息里，以 `tool_result` block 的形式出现。 |
| **assistant 消息要原样回传** | 模型返回的 `content`（包括 `tool_use`、`thinking` 块）必须**原封不动**放回 messages，下一轮模型才能"记得"自己发起过哪个工具调用。 |
| **靠 id 配对** | `tool_use.id` ↔ `tool_result.tool_use_id`，一一对应，这是模型把"调用"和"结果"关联起来的唯一依据。 |
| **system 不在 `messages` 列表里** | Anthropic 的 system prompt 是与 `messages` 平级的顶层参数 `system=`，每次请求都要一起传；它不是列表里的一条 `role: "system"` 消息（OpenAI 则相反）。 |

## 2. Anthropic Messages API

### 2.1 请求体（Request）

```python
client.messages.create(
    model="claude-sonnet-5-5",   # 必填
    max_tokens=2000,             # 必填！OpenAI 里是可选的，这里不填会报错
    messages=[...],              # 必填
    system="You are ...",        # 可选
    tools=[...],                 # 可选
    tool_choice={"type": "auto"},# 可选
    temperature=1.0,             # 可选
    stop_sequences=["###"],      # 可选
    stream=False,                # 可选
    thinking={...},              # 可选，扩展思考
    metadata={"user_id": "..."}, # 可选
)
```

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `model` | string | ✅ | 模型 ID。用兼容端点时（如本项目的 `deepseek-flash`）填对方的模型名。 |
| `max_tokens` | int | ✅ | **本次回复**最多生成多少 token（不是上下文长度）。达到上限时 `stop_reason = "max_tokens"`，回复被截断。 |
| `messages` | list[Message] | ✅ | 对话历史，见 2.2。 |
| `system` | string \| list[TextBlock] | ❌ | 系统提示词。也可以写成 `[{"type": "text", "text": "...", "cache_control": {"type": "ephemeral"}}]` 以便做 prompt caching。 |
| `tools` | list[Tool] | ❌ | 可调用的工具定义，见 2.4。 |
| `tool_choice` | object | ❌ | 控制是否/如何调用工具，见 2.4。 |
| `temperature` | float | ❌ | 采样温度，0~1。 |
| `top_p` / `top_k` | float / int | ❌ | 采样参数，一般不必和 temperature 同时调。 |
| `stop_sequences` | list[str] | ❌ | 遇到这些字符串就停止生成，`stop_reason = "stop_sequence"`。 |
| `stream` | bool | ❌ | 是否流式返回（SSE）。流式时响应结构完全不同（事件流），后续章节再讲。 |
| `thinking` | object | ❌ | 开启扩展思考，例如 `{"type": "enabled", "budget_tokens": 4000}`；新模型也支持 `{"type": "adaptive"}`。开启后回复中会出现 `thinking` block。 |
| `metadata` | object | ❌ | 目前只有 `user_id`，用于滥用检测，不影响生成。 |

### 2.2 Message 对象

```python
{"role": "user" | "assistant", "content": str | list[ContentBlock]}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `role` | `"user"` \| `"assistant"` | **只有这两种**。没有 `system`，也没有 `tool`。 |
| `content` | string 或 block 列表 | 字符串是简写：`"hello"` 等价于 `[{"type": "text", "text": "hello"}]`。只要涉及工具、图片、思考，就必须用 block 列表。 |

> ⚠️ `content` 的两种形态是最常见的类型陷阱之一：你自己写的 user 消息往往是 `str`，模型返回的 assistant 消息永远是 `list`。遍历 history 时要用 `isinstance(content, list)` 判断（本项目 `01-agent-loop.py:104` 就是这么做的）。

### 2.3 Content Block 全家桶

每个 block 都有 `type` 字段，**`type` 决定了其他字段有哪些**。下面按"谁会产生它"分类。

#### (1) 双方都可以用

**`text` —— 纯文本**

```json
{"type": "text", "text": "当前目录有 3 个文件"}
```

| 字段 | 含义 |
|---|---|
| `type` | 固定 `"text"` |
| `text` | 文本内容 |
| `citations` | （响应中）引用信息，没用到引用功能时为 `null`。回传时可以删掉。 |
| `cache_control` | （请求中，可选）`{"type": "ephemeral"}`，标记 prompt cache 断点。 |

#### (2) 只能由 user 发送

**`image` —— 图片**

```json
{
  "type": "image",
  "source": {"type": "base64", "media_type": "image/png", "data": "iVBORw0KG..."}
}
```

`source.type` 也可以是 `"url"`（配合 `"url": "https://..."`）。`media_type` 支持 `image/jpeg`、`image/png`、`image/gif`、`image/webp`。

**`document` —— PDF / 纯文本文档**

```json
{"type": "document", "source": {"type": "base64", "media_type": "application/pdf", "data": "..."}}
```

**`tool_result` —— 工具执行结果（agent loop 的核心之一）**

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
  "content": "file1.py\nfile2.py",
  "is_error": false
}
```

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `type` | `"tool_result"` | ✅ | 拼错（如 `tool_results`、`toolResult`）直接 400。 |
| `tool_use_id` | string | ✅ | 必须等于上一条 assistant 消息里某个 `tool_use.id`。注意字段名是 `tool_use_id`，**不是** `id`，也不是 OpenAI 的 `tool_call_id`。 |
| `content` | string \| list[text/image block] | ❌ | 工具输出。**必须是字符串或 block 列表**，不能直接塞 dict / int / bytes。要返回结构化数据就先 `json.dumps`。 |
| `is_error` | bool | ❌ | 工具执行失败时设为 `true`，模型会知道"这次失败了"并尝试修正，而不是把错误信息当正常输出。 |

#### (3) 只能由 assistant 产生（你只负责原样回传）

**`tool_use` —— 模型请求调用工具（agent loop 的核心之二）**

```json
{
  "type": "tool_use",
  "id": "toolu_01A09q90qw90lq917835lq9",
  "name": "bash",
  "input": {"command": "ls -la"}
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `type` | `"tool_use"` | 固定值。用它来判断"模型要不要调工具"。 |
| `id` | string | 本次调用的唯一 ID（Anthropic 以 `toolu_` 开头，兼容端点格式可能不同）。回填结果时用。 |
| `name` | string | 要调用的工具名，对应 `tools[].name`。 |
| `input` | **object（已解析的 dict）** | 工具参数，结构符合你定义的 `input_schema`。**注意：Anthropic 给的是 dict，OpenAI 给的是 JSON 字符串**，这是两家最容易混的地方。 |

> SDK 2.3.0 的 `ToolUseBlock` 还带有 `caller`、`toolset_name` 等字段（普通客户端工具场景下为 `None`），回传时用 `exclude_none=True` 去掉即可，见第 6 节。

**`thinking` —— 扩展思考内容**

```json
{"type": "thinking", "thinking": "用户想看目录，我应该先 ls...", "signature": "EqQBCgIYAhIM..."}
```

| 字段 | 含义 |
|---|---|
| `thinking` | 模型的思考过程（可能是摘要）。 |
| `signature` | 服务端签名，用于校验思考内容未被篡改。**回传时必须保持原样**，改一个字节都会报错。 |

**`redacted_thinking` —— 被加密的思考内容**

```json
{"type": "redacted_thinking", "data": "EmwKAhgBEgy3va3pzix/LafPsn4a..."}
```

内容不可读，但同样要原样回传。

> ⚠️ 开启 thinking 且使用工具时，**带 `tool_use` 的那条 assistant 消息里的 thinking block 必须和 tool_use 一起回传**，否则下一轮请求会报错。最简单的做法就是：assistant 的 `content` 整体原样保存，不要挑挑拣拣。

**服务端工具相关**（了解即可）：`server_tool_use`、`web_search_tool_result` 等，出现在使用 Anthropic 托管工具（如 web search）时，由服务端执行，你只需原样回传。

### 2.4 工具定义（tools）与 tool_choice

```python
TOOLS = [
    {
        "name": "bash",
        "description": "Run a shell command.",
        "input_schema": {
            "type": "object",
            "properties": {"command": {"type": "string", "description": "要执行的命令"}},
            "required": ["command"],
        },
    }
]
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `name` | ✅ | 工具名，需匹配 `^[a-zA-Z0-9_-]{1,64}$`，不能有空格、点号、中文。 |
| `description` | 强烈建议 | 模型决定"何时用、怎么用"这个工具的**唯一依据**，写得越具体越好。 |
| `input_schema` | ✅ | JSON Schema，顶层必须是 `"type": "object"`。字段名是 `input_schema`（OpenAI 里叫 `parameters`）。 |
| `cache_control` | ❌ | prompt caching 断点。 |

`tool_choice` 取值：

| 值 | 含义 |
|---|---|
| `{"type": "auto"}` | 默认（传了 tools 时）。模型自行决定是否调用。 |
| `{"type": "any"}` | 必须调用某个工具，选哪个由模型决定。 |
| `{"type": "tool", "name": "bash"}` | 必须调用指定工具。 |
| `{"type": "none"}` | 禁止调用工具。 |

以上都可以加 `"disable_parallel_tool_use": true`，限制模型一次最多只发起一个工具调用。

### 2.5 响应体（Response）与 stop_reason

```json
{
  "id": "msg_01XFDUDYJgAACzvnptvVoYEL",
  "type": "message",
  "role": "assistant",
  "model": "claude-sonnet-5-5",
  "content": [
    {"type": "text", "text": "我先看看目录。"},
    {"type": "tool_use", "id": "toolu_01...", "name": "bash", "input": {"command": "ls"}}
  ],
  "stop_reason": "tool_use",
  "stop_sequence": null,
  "usage": {
    "input_tokens": 512,
    "output_tokens": 48,
    "cache_creation_input_tokens": 0,
    "cache_read_input_tokens": 0
  }
}
```

| 字段 | 含义 |
|---|---|
| `id` | 本次响应 ID（`msg_` 开头），排查问题时有用，**不需要**放进 messages。 |
| `type` | 固定 `"message"`。 |
| `role` | 固定 `"assistant"`。 |
| `model` | 实际使用的模型。 |
| `content` | **唯一需要追加进 messages 的东西**（配上 `role: "assistant"`）。 |
| `stop_reason` | 模型为什么停下，见下表。 |
| `stop_sequence` | 如果因 `stop_sequences` 停止，这里是命中的那个字符串。 |
| `usage` | token 用量。**做上下文压缩时就靠它判断上下文是否快满了。** |

`stop_reason` 取值（SDK 2.3.0 的 `StopReason` 类型）：

| 值 | 含义 | agent loop 中如何处理 |
|---|---|---|
| `end_turn` | 模型自然说完了 | 退出循环，等待用户输入。 |
| `tool_use` | 模型要调用工具 | 执行工具，回填 `tool_result`，继续循环。 |
| `max_tokens` | 达到 `max_tokens` 被截断 | 回复不完整；如果截在 `tool_use` 中间，`input` 可能残缺。可加大 `max_tokens` 或让模型"继续"。 |
| `stop_sequence` | 命中自定义停止词 | 按业务处理。 |
| `pause_turn` | 服务端工具（如 web search）长时间运行时暂停 | 把响应原样追加后再次请求，让它继续。 |
| `refusal` | 模型出于安全原因拒绝 | 停止循环，向用户说明。 |
| `model_context_window_exceeded` | 输入 + 输出超出上下文窗口 | 需要压缩上下文——后续"context 压缩"章节的触发点之一。 |

> 💡 本项目的 `01-agent-loop.py` 用"content 里有没有 `tool_use` block"来判断是否继续循环，效果上等价于 `stop_reason == "tool_use"`。更严谨的写法是两者都看，并对 `max_tokens` 单独处理。

### 2.6 一次完整 agent loop 的 messages 演变

用户输入"当前目录下有几个 py 文件？"，下面是每一步之后 `messages` 的完整内容（纯 JSON，即发给 API 的真实形态）。

**第 0 步：用户输入**

```json
[
  {"role": "user", "content": "当前目录下有几个 py 文件？"}
]
```

**第 1 步：模型返回 tool_use，原样追加**

```json
[
  {"role": "user", "content": "当前目录下有几个 py 文件？"},
  {"role": "assistant", "content": [
    {"type": "text", "text": "我来查一下。"},
    {"type": "tool_use", "id": "toolu_A1", "name": "bash", "input": {"command": "ls *.py | wc -l"}}
  ]}
]
```

**第 2 步：执行工具，以 user 身份回填 tool_result**

```json
[
  {"role": "user", "content": "当前目录下有几个 py 文件？"},
  {"role": "assistant", "content": [
    {"type": "text", "text": "我来查一下。"},
    {"type": "tool_use", "id": "toolu_A1", "name": "bash", "input": {"command": "ls *.py | wc -l"}}
  ]},
  {"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_A1", "content": "1"}
  ]}
]
```

**第 3 步：再次调用模型，模型给出最终回答（stop_reason = end_turn），循环结束**

```json
[
  ...,
  {"role": "assistant", "content": [
    {"type": "text", "text": "当前目录下有 1 个 py 文件：01-agent-loop.py。"}
  ]}
]
```

**并行工具调用**：如果模型一次返回多个 `tool_use`，下一条 user 消息里就要有**同样数量**的 `tool_result`，每个对应一个 id，**全部放在同一条 user 消息里**（不要拆成多条）：

```json
{"role": "assistant", "content": [
  {"type": "tool_use", "id": "toolu_B1", "name": "bash", "input": {"command": "pwd"}},
  {"type": "tool_use", "id": "toolu_B2", "name": "bash", "input": {"command": "whoami"}}
]},
{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "toolu_B1", "content": "/Users/lance/..."},
  {"type": "tool_result", "tool_use_id": "toolu_B2", "content": "lance"}
]}
```

### 2.7 结构约束（API 会校验的规则）

违反以下任何一条，API 都会返回 400：

1. **role 只能是 `user` / `assistant`**。
2. **第一条消息应是 `user`**；相邻同角色的消息会被合并，但建议自己保持 user/assistant 交替，便于推理和调试。
3. **每个 `tool_use` 都必须在紧接着的下一条 user 消息里有对应的 `tool_result`**。不能漏、不能隔一条再回、不能 id 对不上。
   - 典型事故：用户在工具执行时按了 Ctrl+C，messages 里留下一条"只有 tool_use 没有 tool_result"的 assistant 消息，之后每次请求都报错。处理办法：中断时补一个 `is_error: true` 的 tool_result，或者把那条 assistant 消息删掉。
4. **在包含 `tool_result` 的 user 消息里，`tool_result` block 必须排在该消息 `content` 列表的最前面**，想附加文字说明（如 `<system-reminder>`）就放在它们后面。示例见本节末尾。
5. **`tool_result` 不能出现在 assistant 消息里，`tool_use` 不能出现在 user 消息里。**
6. **thinking / redacted_thinking block 不能修改**，且在工具调用链中必须回传。
7. **最后一条消息可以是 assistant**——这叫 prefill，模型会从那段文字后面接着写（启用 thinking 时不支持）。agent loop 里一般用不到，但如果你不小心在 assistant 消息后面直接发请求，就会意外触发这个行为。

#### 示例："同一条 user 消息，tool_result 排在最前"

这条规则说的是**一条 user 消息的 `content` 列表内部**的结构，不是指这条消息在整个 messages 里的位置：

- **同一条**：这一轮所有的 `tool_result` 都放进**一个** `{"role": "user", "content": [...]}`；
- **排在最前**：如果这条消息里还有其他 block（文字说明、`<system-reminder>` 等），所有 `tool_result` 必须排在它们前面。

`01-agent-loop.py` 的写法天然满足这两点：先把结果收集进 `results`，循环结束后只追加一次，而且 `results` 里只有 `tool_result`：

```python
results = []
for block in tool_calls:
    output = execute_bash(block.input["command"])
    results.append({"type": "tool_result", "tool_use_id": block.id, "content": output})

messages.append({"role": "user", "content": results})   # 只追加一次 → 同一条 user 消息
```

当你往这条消息里加入其他内容时（比如 hook 输出、状态提醒），就要注意顺序：

```python
# ✅ 正确：先放所有 tool_result，再放其他内容
{"role": "user", "content": [
    {"type": "tool_result", "tool_use_id": "toolu_A1", "content": "..."},
    {"type": "tool_result", "tool_use_id": "toolu_A2", "content": "..."},
    {"type": "text", "text": "<system-reminder>文件已被修改</system-reminder>"},
]}

# ❌ 错误：text 排在了 tool_result 前面
{"role": "user", "content": [
    {"type": "text", "text": "<system-reminder>文件已被修改</system-reminder>"},
    {"type": "tool_result", "tool_use_id": "toolu_A1", "content": "..."},
]}
```

另一种常见错误来自 OpenAI 的习惯（OpenAI 是每个结果一条 `role: tool` 消息）：

```python
# ❌ 每个 tool_result 单独追加一条 user 消息 → 出现连续多条 user 消息
for block in tool_calls:
    messages.append({"role": "user", "content": [{"type": "tool_result", ...}]})
```

官方 API 可能会把连续的 user 消息合并，但兼容端点不一定这样处理，结构也不清晰，不建议这么写。

多个 `tool_result` 之间的先后顺序不要求和 `tool_use` 一致，靠 id 配对即可；不过按 `tool_use` 的顺序排，调试时更容易对照。

## 3. OpenAI Chat Completions API

这是被"兼容"得最多的格式（DeepSeek、通义、Kimi、vLLM、Ollama 等都提供 OpenAI 兼容端点）。和 Anthropic 的核心差异：**有 `system` 和 `tool` 两个额外角色；工具调用放在 `tool_calls` 字段而不是 content block 里；参数是 JSON 字符串。**

### 3.1 请求体

```python
client.chat.completions.create(
    model="gpt-...",
    messages=[...],
    tools=[...],
    tool_choice="auto",
    max_completion_tokens=2000,   # 可选（老字段名 max_tokens）
    temperature=1.0,
)
```

### 3.2 四种角色的消息

```json
// system（新模型也叫 developer）
{"role": "system", "content": "You are a coding agent."}

// user
{"role": "user", "content": "当前目录下有几个 py 文件？"}

// assistant —— 发起工具调用时
{
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_abc123",
      "type": "function",
      "function": {
        "name": "bash",
        "arguments": "{\"command\": \"ls *.py | wc -l\"}"
      }
    }
  ]
}

// tool —— 工具结果，每个调用一条
{"role": "tool", "tool_call_id": "call_abc123", "content": "1"}
```

| 字段 | 含义 / 注意事项 |
|---|---|
| `role` | `system` / `developer` / `user` / `assistant` / `tool`。 |
| `content` | user 可以是 string 或 parts 列表（`{"type": "text", "text": ...}`、`{"type": "image_url", "image_url": {"url": ...}}`）。assistant 在纯工具调用时为 `null`。 |
| `tool_calls[].id` | 调用 ID，`call_` 开头。 |
| `tool_calls[].type` | 固定 `"function"`。 |
| `tool_calls[].function.name` | 工具名。 |
| `tool_calls[].function.arguments` | **JSON 字符串！**需要 `json.loads()` 才能用；而且模型可能生成非法 JSON，要 try/except。 |
| `tool_call_id` | tool 消息里对应的调用 ID。 |
| `reasoning_content` | **非标准字段**，DeepSeek 等推理模型的 OpenAI 兼容端点用它返回思考过程。各家对是否需要回传要求不同，以对方文档为准。 |

**和 Anthropic 最大的结构差异**：多个工具结果在 Anthropic 里是"一条 user 消息、多个 tool_result block"，在 OpenAI 里是"**多条** `role: tool` 消息"。

### 3.3 工具定义

```json
{
  "type": "function",
  "function": {
    "name": "bash",
    "description": "Run a shell command.",
    "parameters": {
      "type": "object",
      "properties": {"command": {"type": "string"}},
      "required": ["command"]
    }
  }
}
```

比 Anthropic 多包了一层 `{"type": "function", "function": {...}}`，schema 字段叫 `parameters`。

### 3.4 响应体

```json
{
  "id": "chatcmpl-...",
  "object": "chat.completion",
  "model": "...",
  "choices": [
    {
      "index": 0,
      "message": {"role": "assistant", "content": null, "tool_calls": [...]},
      "finish_reason": "tool_calls"
    }
  ],
  "usage": {"prompt_tokens": 512, "completion_tokens": 48, "total_tokens": 560}
}
```

- 要追加进 messages 的是 `choices[0].message`。
- `finish_reason` 取值：`stop`（≈ end_turn）、`tool_calls`（≈ tool_use）、`length`（≈ max_tokens）、`content_filter`（≈ refusal）。
- `usage` 字段名是 `prompt_tokens` / `completion_tokens`，Anthropic 是 `input_tokens` / `output_tokens`。

## 4. OpenAI Responses API（简述）

OpenAI 较新的接口（`client.responses.create`），把对话建模成一串**扁平的 item**，而不是"消息套 block"：

```json
[
  {"type": "message", "role": "user", "content": "当前目录下有几个 py 文件？"},
  {"type": "function_call", "call_id": "call_abc", "name": "bash", "arguments": "{\"command\": \"ls *.py | wc -l\"}"},
  {"type": "function_call_output", "call_id": "call_abc", "output": "1"},
  {"type": "message", "role": "assistant", "content": [{"type": "output_text", "text": "有 1 个。"}]}
]
```

特点：

- 工具调用和工具结果都是**独立的 item**，用 `call_id` 配对；不再需要伪装成 user/tool 角色。
- 系统提示词走顶层 `instructions` 参数。
- 推理模型会产生 `{"type": "reasoning", ...}` item，需要回传（或用服务端状态 `previous_response_id` 代替自己维护历史）。

它的思想和 Anthropic 的 block 模型很接近：**"消息"只是容器，真正有语义的是 typed item/block。**

## 5. 三种格式字段对照表

| 概念 | Anthropic Messages | OpenAI Chat Completions | OpenAI Responses |
|---|---|---|---|
| 系统提示 | 顶层 `system` | `{"role": "system"}` 消息 | 顶层 `instructions` |
| 角色 | `user` / `assistant` | `system` / `user` / `assistant` / `tool` | item 的 `type` + `role` |
| 输出上限 | `max_tokens`（**必填**） | `max_completion_tokens`（可选） | `max_output_tokens`（可选） |
| 工具定义外层 | `{name, description, input_schema}` | `{type: "function", function: {name, description, parameters}}` | `{type: "function", name, description, parameters}` |
| 模型发起调用 | content 中的 `tool_use` block | assistant 消息的 `tool_calls[]` | `function_call` item |
| 调用 ID 字段 | `id` | `id` | `call_id` |
| 调用参数 | `input`（**dict**） | `function.arguments`（**JSON 字符串**） | `arguments`（**JSON 字符串**） |
| 回填结果 | user 消息中的 `tool_result` block | `{"role": "tool"}` 消息 | `function_call_output` item |
| 结果关联字段 | `tool_use_id` | `tool_call_id` | `call_id` |
| 结果内容字段 | `content` | `content` | `output` |
| 标记错误 | `is_error: true` | 无（写进 content 文本） | 无（写进 output 文本） |
| 停止原因 | `stop_reason` | `choices[0].finish_reason` | `status` + output item 类型 |
| "要调工具" | `"tool_use"` | `"tool_calls"` | 输出含 `function_call` |
| "说完了" | `"end_turn"` | `"stop"` | `status: "completed"` 且无 function_call |
| "被截断" | `"max_tokens"` | `"length"` | `status: "incomplete"` |
| token 用量 | `input_tokens` / `output_tokens` | `prompt_tokens` / `completion_tokens` | `input_tokens` / `output_tokens` |
| 思考内容 | `thinking` / `redacted_thinking` block | 非标准 `reasoning_content` | `reasoning` item |

## 6. JSON 序列化问题：SDK 对象 vs 纯 dict

这正是写 agent loop 时最容易踩、也最难一眼看出来的坑。

### 6.1 问题复现

`01-agent-loop.py:57` 是这样追加 assistant 消息的：

```python
messages.append({
    "role": "assistant",
    "content": res.content,   # ← 这里是 SDK 的 pydantic 对象列表，不是 dict！
})
```

`res.content` 的元素是 `anthropic.types.TextBlock`、`ToolUseBlock` 等 **pydantic 模型实例**。
把它们传回 `client.messages.create` 没有问题——SDK 认识自己的类型；但一旦你想：

- 把 history 保存到文件（会话持久化）
- 打印 / 记日志
- 做上下文压缩时数 token、截断、摘要
- 发给另一个 SDK 或 HTTP 接口

就会遇到：

```
>>> json.dumps([ToolUseBlock(id="toolu_01", name="bash", input={"command": "ls"}, type="tool_use")])
TypeError: Object of type ToolUseBlock is not JSON serializable
```

另一个隐蔽问题：history 里**混着两种东西**——你自己写的 dict（user 消息、tool_result）和 SDK 对象（assistant content）。于是同一段遍历代码，有时要写 `block["type"]`，有时要写 `block.type`，`01-agent-loop.py:106` 只好用 `getattr(block, "type", None)` 兜底。

### 6.2 解决办法：在边界处统一转成纯 dict

```python
def to_plain_blocks(content):
    """把 SDK 返回的 content block 对象转成可 JSON 序列化的纯 dict。"""
    return [block.model_dump(exclude_none=True) for block in content]

messages.append({
    "role": "assistant",
    "content": to_plain_blocks(res.content),
})
```

为什么要 `exclude_none=True`？直接 `model_dump()` 会带出一堆值为 `None` 的可选字段：

```python
>>> ToolUseBlock(...).model_dump()
{'id': 'toolu_01', 'caller': None, 'input': {'command': 'ls'}, 'name': 'bash', 'type': 'tool_use', 'toolset_name': None}

>>> ToolUseBlock(...).model_dump(exclude_none=True)
{'id': 'toolu_01', 'input': {'command': 'ls'}, 'name': 'bash', 'type': 'tool_use'}

>>> TextBlock(text="hi", type="text").model_dump()
{'citations': None, 'text': 'hi', 'type': 'text'}
```

官方 API 通常能容忍这些 `null`，但**第三方兼容端点**（如本项目的 DeepSeek）可能不认识 `caller`、`toolset_name` 这类较新的字段而报错。去掉 None 字段最稳妥。

转换后整个 history 都是纯 dict/list/str，可以：

```python
json.dumps(messages, ensure_ascii=False)   # ✅
block["type"]                              # ✅ 统一用下标访问
```

### 6.3 其他会导致序列化失败的值

| 来源 | 问题 | 处理 |
|---|---|---|
| 工具返回 `bytes` | `subprocess` 未设 `text=True` 时输出是 bytes | `text=True, errors="replace"`（本项目已这样做） |
| 工具返回 dict / list / int | `tool_result.content` 只接受 str 或 block 列表 | `json.dumps(result, ensure_ascii=False)` 或 `str(result)` |
| `Path`、`datetime`、`set` 等对象 | 不是 JSON 原生类型 | 放进 messages 前先 `str()` |
| 非法 UTF-8 / 控制字符 | 某些二进制命令输出 | `errors="replace"` |
| 超长输出 | 不是序列化错误，但会撑爆上下文 | 截断（本项目截到 50000 字符），后续 context 压缩章节再系统处理 |

## 7. 常见坑与排查清单

### 7.1 字段名速查（最容易拼错的）

| ✅ 正确 | ❌ 常见错误 |
|---|---|
| `"type": "tool_result"` | `"tool_results"`、`"toolResult"`、`"tool_response"` |
| `"tool_use_id"` | `"id"`、`"tool_id"`、`"tool_call_id"`（这是 OpenAI 的） |
| `"input_schema"` | `"parameters"`（这是 OpenAI 的）、`"inputSchema"`（这是 MCP 的） |
| `"is_error"` | `"error"`、`"isError"` |
| `block.input` 是 dict | 当成字符串去 `json.loads`（那是 OpenAI 的 `arguments`） |
| `system=` 顶层参数 | 在 messages 里放 `{"role": "system"}` |

### 7.2 报错 → 原因对照

| 报错现象 | 可能原因 |
|---|---|
| `messages.N: tool_use ids were found without tool_result blocks immediately after` | 漏回了某个 tool_result；或中断后残留了孤立的 tool_use |
| `unexpected tool_use_id found in tool_result blocks` | `tool_use_id` 写错 / 对应的 assistant 消息被删了（上下文压缩时最容易出现） |
| `max_tokens: Field required` | Anthropic 下 `max_tokens` 是必填项 |
| `tool_result.content: Input should be a valid string` | 工具返回了 dict / None 等非字符串值 |
| `Object of type XxxBlock is not JSON serializable`（本地） | history 里混入了 SDK 对象，见第 6 节 |
| 模型反复调用同一个工具 | 工具结果没有正确回填（比如回填成了空字符串），模型以为没执行 |
| 开启 thinking 后第二轮报错 | assistant 消息里的 thinking block 被丢弃或修改了 |

> 具体报错文本因 API 版本和兼容端点而异，以上为典型措辞，按关键词匹配即可。

### 7.3 写 agent loop 的检查清单

- [ ] assistant 的 `content` 整体保存，不要只保存 text
- [ ] 保存前用 `model_dump(exclude_none=True)` 转成纯 dict
- [ ] 每个 `tool_use` 都产出一个 `tool_result`，`tool_use_id` 一一对应
- [ ] 同一轮的所有 `tool_result` 放进**同一条** user 消息，并排在该消息 `content` 列表的最前面，其他 block 放在后面（见 2.7 末尾示例）
- [ ] `tool_result.content` 一定是字符串（或 text/image block 列表）
- [ ] 工具异常时也要回填结果，并设置 `is_error: true`，不要让异常打断 loop
- [ ] 用户中断（Ctrl+C）时，确保不留下孤立的 `tool_use`
- [ ] 区分 `stop_reason`：`tool_use` 继续、`end_turn` 退出、`max_tokens` 特殊处理
- [ ] 记录 `usage`，为后续 context 压缩做准备
- [ ] 调试时 `print(json.dumps(messages, ensure_ascii=False, indent=2))` 看看真实发出去的是什么

## 8. SYSTEM、Prompt Caching 与轻量化 CLAUDE.md

### 8.1 system 与 messages 的关系

`system` 不在 `messages` 列表里，而是与 `messages`、`tools` 平级的顶层参数。每次调用 `create()`，三者会一起发给服务端：

```json
{
  "tools":    [ ... ],
  "system":   "You are a coding agent at ...",
  "messages": [ {"role": "user", ...}, {"role": "assistant", ...}, ... ]
}
```

服务端按 `tools → system → messages` 的顺序把它们拼成模型实际看到的输入。所以模型"看得到" system，只是在 API 层面，它被放在对话历史之外。

单独拿出来的好处：

- `messages` 里只有 user / assistant 两种角色，一问一答的结构更干净；
- system 是会话级的全局设定（身份、规则、环境），整个会话基本不变，适合做缓存（见 8.3）；
- 持久化会话时要注意：`history` 里**没有** system，恢复会话时要重新传入。

### 8.2 每次传入不同的 system 会怎样

API 允许每次传不同的 system，模型也不会记得"上一次的 system"，因为每次请求都是独立的。但这样做有两个影响：

**(1) 行为上：模型会用新规则重新看待全部历史**

新 system 立即生效，而且作用于整段历史，不是"从这一轮起"才生效。如果新规则和历史矛盾（比如工作目录从 `/a` 改成 `/b`，但历史里一直在 `/a` 下操作），模型可能困惑或出错。另外，模型会模仿上下文里自己以往的做法，历史越长，旧行为的"惯性"越强。

**(2) 成本上：前缀缓存全部失效**

system 排在很靠前的位置，改动它会导致后面整段历史都要重新计算，原因见 8.3。

**实践原则：system 保持稳定，变化的信息追加到 messages 末尾。**

```python
messages.append({
    "role": "user",
    "content": "<system-reminder>工作目录已切换到 /b</system-reminder>\n继续刚才的任务",
})
```

这样前缀不变、缓存依然有效；变化也有明确的时间点，模型能看出"之前在 /a，从这里开始在 /b"，历史和现状不再矛盾。

### 8.3 Prompt Caching 缓存的是什么

prompt caching **不是**让客户端更快地拼接提示词（拼接字符串几乎不花时间），而是发生在**模型提供方（Anthropic / DeepSeek 等）的 API 服务器**上的优化，**不是你自己写的 agent 程序**要做的事。它缓存的是模型**读完这段前缀之后的计算结果**。

```
你的 agent（01-agent-loop.py）          模型提供方的服务器（Anthropic / DeepSeek）
──────────────────────────           ──────────────────────────────────────
拼 tools + system + messages  ──HTTP──▶  预填充：计算每个 token 的 KV
                                         ↑ prompt cache 在这里：
                                           前缀和上次一样 → 直接复用已存的 KV
                              ◀──HTTP──  解码生成回复 + usage（含缓存命中情况）
```

agent 程序也不可能自己做这个缓存：KV 是模型内部的中间计算结果，体量很大，存在服务商的 GPU 和存储上，客户端既拿不到也用不上。

模型处理一个请求分两个阶段：

```
预填充（prefill）：把整段输入读一遍，为每个 token 计算注意力用的 Key/Value 张量（KV cache）
解码（decode）  ：在这些 KV 的基础上逐个生成输出 token
```

agent 每轮都要重发完整历史，第 50 轮时可能有 10 万 token 已经在第 49 轮算过了。prompt caching 把这段前缀的 KV 存下来，下次遇到**完全相同的前缀**就直接复用：

- **首 token 延迟降低**：长上下文下，预填充是延迟的大头；
- **费用降低**：Anthropic 对命中缓存的输入 token 按基础输入价的约 1/10 计费，写入缓存会稍贵（5 分钟 TTL 约 1.25 倍，1 小时 TTL 约 2 倍）。

**为什么必须是"前缀"**：Transformer 的注意力是因果的，每个 token 的 KV 都依赖它**前面所有的** token。第 i 个 token 一变，它后面所有 token 的 KV 都得重算。所以拼接顺序是 `tools → system → messages`：**越稳定的内容放得越靠前**。

| 角色 | 负责什么 |
|---|---|
| 模型服务端 | 存储和复用 KV、管理过期时间（Anthropic 默认 5 分钟，命中后续期；可选 1 小时） |
| agent 客户端 | **保持前缀稳定**；Anthropic 需要用 `cache_control: {"type": "ephemeral"}` 标出缓存断点；DeepSeek、OpenAI 等是自动做前缀缓存 |

对写 agent 的人来说，prompt caching 不需要自己实现，它是一条**约束**：**不改历史、不动前缀、变化追加到末尾**。可以从响应的 `usage.cache_read_input_tokens` / `cache_creation_input_tokens` 观察是否命中缓存。使用兼容端点（如 DeepSeek）时，这两个字段是否如实返回以对方文档或实际返回为准，打印一下 `res.usage` 即可确认。

> 唯一"合理地"破坏缓存的时机是上下文压缩：把旧历史替换成摘要，相当于一次性付出重算的代价，换来更短的上下文。

### 8.4 案例：Claude Code 是怎么组织 system 的

Claude Code 会把每次会话记录在 `~/.claude/projects/<编码后的项目路径>/<session-id>.jsonl`。其中 `api-request-shape` 记录了实际发出的 `system` 和 `tools`。下面是从某个会话（Claude Code 2.1.311）里观察到的结构。注意这是内部格式，没有官方文档，不同版本可能变化。

**system 本身很小，只放稳定内容：**

| 部分 | 内容 | 大小 |
|---|---|---|
| `system[0]` | 身份声明："You are Claude Code, Anthropic's official CLI for Claude." | 57 字符 |
| `system[1]` | 基础行为规则（输出展示、权限模式、如何对待 system-reminder 等） | 约 2.7k 字符 |
| `system[2]` | 会话相关：使用指引、记忆目录、环境信息、上下文管理 | 约 6.2k 字符 |
| `tools` | 工具的完整 schema（Bash、Read、Edit……），与 system 平级 | — |

**大块的上下文，作为 `<system-reminder>` 注入在第一条 user 消息里：**

| attachment 类型 | 内容 |
|---|---|
| `instructions` | CLAUDE.md 以及 `~/.claude/rules/` 下的规则文件 |
| `skill_listing` | 所有可用 skill 的名称和一句话描述 |
| `agent_listing_delta` | 可用的子 agent 列表 |
| `deferred_tools_delta` | 延迟加载的工具名单（只给名字，要用时再拉 schema） |
| `mcp_instructions_delta` | MCP 服务器的使用说明 |
| `environment` / `model` / `date` | 工作目录、平台、模型、日期等 |

类型名里的 `_delta` 说明：会话中途有变化时（比如接入了新的 MCP 工具），Claude Code 不改 system，而是往 messages 里追加一条增量说明。

**对话过程中 system 基本保持不变。** 观察到的那个会话里，20 多次 API 请求的 `shapeHash`（system + tools 的指纹）完全相同，每轮都能命中前缀缓存。各种变化（hook 输出、文件被外部修改、日期变化、权限模式切换……）都以 `<system-reminder>` 的形式追加。

| 场景 | system | messages |
|---|---|---|
| 正常对话 | 不变 | 只追加 |
| 自动压缩 / `/compact` | 原样重发 | 旧历史替换为**摘要** + 最近内容；CLAUDE.md 等指令重新注入 |
| `/clear` | 重新生成 | 清空，相当于新会话 |
| `--resume` / `--continue` | 按当前环境**重新生成** | 从 jsonl 恢复 |

用户能影响 system 的入口：`--append-system-prompt`（追加）、`--system-prompt`（整体替换，慎用）、output styles。CLAUDE.md 虽然常被当作"系统提示"，但实际是注入在 messages 里的。用 `/context` 命令可以看到各部分占用的 token 数。

### 8.5 为什么推荐轻量化的 CLAUDE.md / AGENTS.md

CLAUDE.md 位于 `messages[0]`，位置非常靠前。但它通常只在会话开始（以及压缩后）加载，会话中途改了文件也不会回头修改 `messages[0]`。所以**保护缓存不是推荐轻量化的主要原因**，真正的原因是：

1. **上下文预算**：它出现在每个会话的每次请求里。就算命中缓存，也占着上下文窗口，按缓存读取价计费。
2. **注意力被稀释**：指令越长，模型对每一条的遵守程度越低。
3. **大部分内容只和少数任务相关**：比如"数据库迁移怎么写"，只有改数据库时才需要。

核心思想是**按需加载（progressive disclosure）**：CLAUDE.md 只写提纲和指针，细节放在别的文件里，需要时再读。

**怎么"指向"别的文件很关键：**

```markdown
# CLAUDE.md

## 方式 A：@ 导入 —— 加载时立即展开，不省上下文
@docs/database-guide.md

## 方式 B：文字指针 —— 真正的按需加载
- 修改数据库相关代码前，先阅读 docs/database-guide.md
- 写测试时参考 docs/testing.md
```

| 方式 | 何时进入上下文 | 是否节省上下文 |
|---|---|---|
| `@path` 导入 | 加载 CLAUDE.md 时立即展开 | ❌ 只方便拆分维护 |
| 文字指针 | 模型判断需要时用 Read 工具读取，以 `tool_result` 的形式追加到末尾 | ✅ 而且不破坏前缀缓存 |
| 子目录 CLAUDE.md | 模型读写该目录下的文件时才加载 | ✅ |
| Skills | 启动时只加载名称和描述，用到时才读完整内容 | ✅ |

### 8.6 对照到自己的 agent

```
TOOLS          ← 固定：工具 schema，会话期间不改
SYSTEM_PROMPT  ← 固定：身份 + 规则 + 环境 + skill 名称清单 + "项目说明见 AGENTS.md"
messages[0]    ← 用户的第一个问题（可附带轻量 AGENTS.md 作为 reminder）
...
tool_use(read_file) → tool_result(完整的 skill / 文档内容)   ← 按需加载，追加在末尾
<system-reminder>…</system-reminder>                         ← 运行时的状态变化，追加在末尾
```

后续实现 skill 加载和上下文压缩时，牢记两条：

- **skill 加载**：system 里只放清单，完整内容通过工具调用按需读入，不要每轮重新生成 system；
- **上下文压缩**：只动 `messages`，不动 `system` 和 `tools`。压缩后注意不要留下孤立的 `tool_use` / `tool_result`（见 2.7）。

### 8.7 实践：mini agent 如何加载 CLAUDE.md

**(1) 不要在启动时单独发一条 user 消息**

如果启动时就把 CLAUDE.md 作为一条独立的 user 消息发出去：

- 这次请求会**产生一次模型回复**（比如"好的，我已了解项目规则"），浪费一次调用，还在历史里留下一段没用的对话；
- 如果只追加到 messages 而不发请求，等用户真正提问时，就会出现连续两条 user 消息。

而且缓存不需要"预热"：**第一次真实请求时缓存就会写入**，第二轮开始就能命中。

更好的做法是参考 Claude Code：**把 CLAUDE.md 作为额外的 block，附加到用户的第一条消息里**，不额外发请求：

```python
def build_first_user_message(query, instructions):
    blocks = []
    if instructions:
        blocks.append({
            "type": "text",
            "text": f"<system-reminder>\n# Project instructions (CLAUDE.md)\n{instructions}\n</system-reminder>",
        })
    blocks.append({"type": "text", "text": query})
    return {"role": "user", "content": blocks}


# main 里：只有第一轮才附加
if not history:
    history.append(build_first_user_message(query, load_claude_md()))
else:
    history.append({"role": "user", "content": query})
```

**(2) 放在 system 里还是 messages[0] 里？**

对缓存来说**两种都可以**：缓存只要求这段内容**位置靠前，并且之后不再修改**。选哪种取决于其他方面的取舍：

| | 拼进 `SYSTEM_PROMPT` | 附加到 `messages[0]`（Claude Code 的做法） |
|---|---|---|
| 实现难度 | 最简单，一行字符串拼接 | 稍复杂，要区分第一轮 |
| 恢复会话 | 要重新读取 CLAUDE.md 并生成 system | 已经在 history 里，恢复时自动带上 |
| 上下文压缩 | 不受影响，system 不会被压缩 | `messages[0]` 会被摘要替换，**压缩后要重新注入** |
| system 的复用 | 每个项目的 system 都不同 | system 在所有项目间完全一致，前缀可以跨项目复用 |

Claude Code 选择 messages[0]，主要是因为用户和项目非常多，让 system 保持完全一致更划算。对 mini agent 来说：

- **起步阶段**：直接拼进 `SYSTEM_PROMPT`，简单可靠；
- **做到会话恢复和上下文压缩时**：再改成 messages[0] 注入的方式，顺便练习"压缩后重新注入"这个技术点。

**(3) 两个要先知道的事实**

- **把 CLAUDE.md 放在前面，是因为模型需要这些信息，不是因为缓存。** 缓存原则只要求一件事：**放好之后就别再改**。会话中途 CLAUDE.md 被修改了，也不要回头改 `messages[0]` 或 system；可以在末尾追加一条 reminder，或者等下次会话再生效。
- **太短的前缀不会被缓存。** Anthropic 对可缓存的前缀有最小长度要求（多数模型约 1024 token），并且需要用 `cache_control` 显式标记。DeepSeek 是自动缓存，也有自己的粒度规则。system prompt 很短时，前几轮看不到缓存命中，历史变长后才看得出效果，可以打印 `res.usage` 观察。

**(4) 总结**

```
SYSTEM_PROMPT   ← 内置规则 + （起步阶段）CLAUDE.md 内容     不变
TOOLS           ← 工具定义                                  不变
messages[0]     ← （进阶做法）<system-reminder>CLAUDE.md</system-reminder> + 用户第一个问题
messages[1..]   ← 只追加
```

不需要启动时就发请求。第一次真实请求会把稳定的前缀一起带上，缓存就从那时开始生效。
