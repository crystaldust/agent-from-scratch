# 01. Agent Loop（Go 版）—— context.Context 与 history 类型详解

> 用 Go SDK（`github.com/anthropics/anthropic-sdk-go/v2`）写 agent loop 时，每次调用 `client.Messages.New` 的第一个参数都是 `ctx`。
> agent loop 一轮可能跑好几分钟、连续执行多个工具，**能不能随时干净地停下来**（Ctrl+C、超时）全靠它。

> 第 10 节讲多返回值（如 `os.Getwd()`）的错误处理，以及函数外（包级别）能写什么、不能写什么。

> 第 12 节讲怎么解析响应：判断内容块是不是 `tool_use`，以及取出工具输入里的字段（如 bash 的 `command`）。

## 1. context 是什么

`context.Context` 是标准库 `context` 包里的接口，用来告诉一个操作**什么时候该停下**。它主要做三件事：

| 作用 | 说明 |
|---|---|
| **取消（cancel）** | 调用方不想等了，主动叫停正在进行的操作 |
| **超时 / 截止时间（deadline）** | 超过某个时长或时间点，自动中止 |
| **传递请求级数据（value）** | 比如 trace ID。用得较少，学习阶段可以先不管 |

Go 的惯例：**凡是可能阻塞、要走网络或 IO 的函数，第一个参数都是 `ctx context.Context`**。不只是 Anthropic SDK，`net/http`、`os/exec`、数据库驱动、gRPC 都是这么设计的。

ctx 被取消后：

- `ctx.Done()` 返回的 channel 会被关闭，可以用 `select` 监听
- `ctx.Err()` 返回原因：`context.Canceled`（被主动取消）或 `context.DeadlineExceeded`（超时）
- 拿着这个 ctx 的 SDK 调用、HTTP 请求、子进程会被中止，并返回对应的错误

## 2. 常见的创建方式

### 2.1 不需要任何控制：`context.Background()`

```go
resp, err := client.Messages.New(context.Background(), params)
```

空 context，永远不会被取消，也没有超时。适合 demo 或者作为整棵 context 树的根。

### 2.2 加超时：`context.WithTimeout`

```go
ctx, cancel := context.WithTimeout(context.Background(), 60*time.Second)
defer cancel() // 一定要调用，释放计时器等资源

resp, err := client.Messages.New(ctx, params)
if errors.Is(err, context.DeadlineExceeded) {
    fmt.Println("请求超时")
}
```

### 2.3 手动取消：`context.WithCancel`

```go
ctx, cancel := context.WithCancel(context.Background())
// 在别的地方（另一个 goroutine）调用 cancel()，所有拿着 ctx 的操作都会停下
```

> `WithTimeout`、`WithCancel` 返回的 `cancel` 函数**必须调用**，通常是紧跟着写 `defer cancel()`。忘了调用会泄漏资源，`go vet` 也会报警告。

## 3. signal.NotifyContext：把 Ctrl+C 变成取消信号

`signal.NotifyContext` 是标准库 `os/signal` 包里的函数（Go 1.16 起才有）。它返回一个 context，**进程收到指定的系统信号时，这个 context 会被自动取消**。

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
```

| 参数 / 返回值 | 含义 |
|---|---|
| 第一个参数 | 父 context |
| `os.Interrupt` | 在终端按 Ctrl+C 时收到（SIGINT） |
| `syscall.SIGTERM` | `kill <pid>`、Docker 停容器、k8s 关 Pod 时发的 |
| `ctx` | 收到其中任一信号时被取消 |
| `stop` | 停止监听，信号的处理恢复成默认行为 |

### 3.1 它解决什么问题

默认情况下按 Ctrl+C，Go 程序会被**立刻杀掉**：进行中的请求没收尾，对话历史没保存，`defer` 也不会执行。

用了 `NotifyContext` 以后，信号被"接住"，变成 context 取消：

1. 进行中的 `client.Messages.New(ctx, ...)` 马上中止，返回 `context.Canceled`
2. 代码判断出这个错误后正常 `return`，`defer` 都会执行
3. 程序体面地退出

### 3.2 它等价于什么

`NotifyContext` 其实是对下面这段代码的封装：

```go
ctx, cancel := context.WithCancel(context.Background())
sigCh := make(chan os.Signal, 1)
signal.Notify(sigCh, os.Interrupt)
go func() {
    <-sigCh
    cancel()
}()
```

### 3.3 坑：第二次 Ctrl+C 没反应

调用 `stop()` 之前，信号会**一直被接住**。如果收到第一个信号后收尾逻辑卡住了，用户再怎么按 Ctrl+C 也没反应。

做法：收到第一个信号后马上调用 `stop()`，恢复默认行为。这样第一次 Ctrl+C 是正常退出，第二次 Ctrl+C 就强制杀掉进程：

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
defer stop()

go func() {
    <-ctx.Done()
    stop() // 再按一次 Ctrl+C 就直接退出
    fmt.Println("\n正在退出，再按一次 Ctrl+C 强制退出")
}()
```

## 4. 父子关系：取消向下传播

context 是一棵树：从父 context 派生出子 context。

- **父被取消，所有子都会被取消**
- **子被取消，不影响父**

```
context.Background()
└── NotifyContext(Ctrl+C)           ← 整个程序的根，main 创建
    ├── WithTimeout(2m)             ← 第 1 轮模型请求
    ├── WithTimeout(2m)             ← 第 2 轮模型请求
    │   └── WithTimeout(30s)        ← 这一轮里的某个 bash 工具
    └── ...
```

```go
root, stop := signal.NotifyContext(context.Background(), os.Interrupt)
defer stop()

for {
    turnCtx, cancel := context.WithTimeout(root, 2*time.Minute) // 每轮单独设超时
    resp, err := client.Messages.New(turnCtx, params)
    cancel()
    // ...
}
```

这样每一轮各自有超时，单轮超时不会影响整个程序；而按一次 Ctrl+C 就能停掉整个 agent。

> **在下层需要更细的控制时，从传进来的 ctx 派生，不要新建 `context.Background()`。** 否则这一层就和 main 的 Ctrl+C 断开了，用户按下中断，这一层收不到。

## 5. 在 agent loop 中传递 ctx

问题：`ctx` 和 `stop` 在 `main` 里创建，但真正调用 `client.Messages.New` 的是 `agentLoop`。

答案：**把 `ctx` 当作 `agentLoop` 的第一个参数传进去，`stop` 留在 `main` 里。**

```go
func main() {
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
    defer stop() // 由 main 负责收尾

    client := anthropic.NewClient()

    if err := agentLoop(ctx, client, "帮我算 2+3"); err != nil {
        if errors.Is(err, context.Canceled) {
            fmt.Println("\n已中断")
            return
        }
        log.Fatal(err)
    }
}

func agentLoop(ctx context.Context, client anthropic.Client, prompt string) error {
    messages := []anthropic.MessageParam{
        anthropic.NewUserMessage(anthropic.NewTextBlock(prompt)),
    }

    for {
        resp, err := client.Messages.New(ctx, anthropic.MessageNewParams{
            Model:     "claude-opus-5-5",
            MaxTokens: 16000,
            Messages:  messages,
        })
        if err != nil {
            return fmt.Errorf("messages.new: %w", err) // 用 %w 包装，main 里的 errors.Is 仍然能认出来
        }

        messages = append(messages, resp.ToParam())
        if resp.StopReason != anthropic.StopReasonToolUse {
            return nil
        }

        toolResults, err := runTools(ctx, resp) // 工具执行也接 ctx
        if err != nil {
            return err
        }
        messages = append(messages, anthropic.NewUserMessage(toolResults...))
    }
}
```

### 5.1 为什么这么分工

| | 职责 | 谁持有 |
|---|---|---|
| `ctx` | "还能不能继续干活"的信号 | 谁干活谁拿着，一路往下传：`main → agentLoop → Messages.New / runTools → 具体工具` |
| `stop` | "信号监听什么时候结束" | 只有 `main`，下层函数不需要知道，也不应该调用 |

### 5.2 Go 的约定

- `ctx` 永远是**第一个参数**，名字就叫 `ctx`
- **不要把 ctx 存进结构体字段**。结构体可以存 `client`、`tools`，但 ctx 要在每次调用时传：

  ```go
  type Agent struct {
      client anthropic.Client
      tools  []anthropic.ToolUnionParam
  }

  func (a *Agent) Run(ctx context.Context, prompt string) error { ... }
  ```

  原因：ctx 对应的是"这一次调用"的生命周期，而结构体通常比一次调用活得更久。把 ctx 存进去，生命周期就混乱了。

- 返回错误时用 `fmt.Errorf("...: %w", err)` 包装，**不要用 `%v`**，否则上层 `errors.Is(err, context.Canceled)` 判断会失效。

## 6. 在 runTools 和工具里使用 ctx

核心思路：**把 ctx 一路传到每个工具函数里，工具内部用支持 ctx 的标准库 API。** 同时要分清两种失败：工具自己出错，和被用户中断。

### 6.1 工具注册表：每个工具都接收 ctx

```go
// 统一的工具函数签名：接收 ctx 和原始 JSON 输入，返回给模型看的文本
type ToolFunc func(ctx context.Context, input json.RawMessage) (string, error)

var toolRegistry = map[string]ToolFunc{
    "bash":      runBash,
    "fetch_url": fetchURL,
}
```

### 6.2 runTools：分发工具调用，区分两种错误

```go
func runTools(ctx context.Context, resp *anthropic.Message) ([]anthropic.ContentBlockParamUnion, error) {
    var results []anthropic.ContentBlockParamUnion

    for _, block := range resp.Content {
        use, ok := block.AsAny().(anthropic.ToolUseBlock)
        if !ok {
            continue
        }

        // 每个工具开始前检查：用户已经按了 Ctrl+C，就不再启动新工具
        if err := ctx.Err(); err != nil {
            return nil, err
        }

        output, err := callTool(ctx, use.Name, use.Input) // Input 本身就是 json.RawMessage，见第 12 节
        switch {
        case errors.Is(err, context.Canceled):
            // 被用户中断：往上返回，终止整个 agent 循环
            return nil, err
        case err != nil:
            // 工具自己出错：作为 is_error 结果交给模型，让它自己调整
            results = append(results, anthropic.NewToolResultBlock(use.ID, err.Error(), true))
        default:
            results = append(results, anthropic.NewToolResultBlock(use.ID, output, false))
        }
    }
    return results, nil
}

func callTool(ctx context.Context, name string, input json.RawMessage) (string, error) {
    fn, ok := toolRegistry[name]
    if !ok {
        return "", fmt.Errorf("unknown tool: %s", name)
    }
    return fn(ctx, input)
}
```

| 失败类型 | 例子 | 处理方式 | 原因 |
|---|---|---|---|
| **工具失败** | 命令返回非 0、单个工具超时、参数不合法 | 返回 `is_error: true` 的 `tool_result` | 这是模型能处理的信息，它通常会换个参数或方法重试 |
| **用户中断** | `context.Canceled` | 往上 `return err`，终止整个循环 | 用户不想继续了，不该告诉模型"工具失败了"让它接着跑 |

### 6.3 工具内部：用支持 ctx 的 API

| 场景 | 支持 ctx 的写法 | ctx 取消时会发生什么 |
|---|---|---|
| 执行 shell 命令 | `exec.CommandContext(ctx, ...)` | 只杀掉它直接启动的 `bash` 进程；`bash` 再启动的子进程默认不会被杀（见第 13 节） |
| 发 HTTP 请求 | `http.NewRequestWithContext(ctx, ...)` | 中断连接，`Do` 返回错误 |
| 调用 Claude | `client.Messages.New(ctx, ...)` | 中止请求，返回 `context.Canceled` |
| 自己写的长循环 | `select { case <-ctx.Done(): ... }` | 由你自己决定怎么退出 |

**执行 shell 命令：`exec.CommandContext`**

```go
const bashTimeout = 30 * time.Second

func runBash(ctx context.Context, input json.RawMessage) (string, error) {
    var in struct {
        Command string `json:"command"`
    }
    if err := json.Unmarshal(input, &in); err != nil {
        return "", fmt.Errorf("invalid input: %w", err)
    }

    // 从父 ctx 派生出单个工具的超时；Ctrl+C 的取消照样会传下来
    toolCtx, cancel := context.WithTimeout(ctx, bashTimeout)
    defer cancel()

    cmd := exec.CommandContext(toolCtx, "bash", "-c", in.Command)
    cmd.WaitDelay = 2 * time.Second // ctx 取消后，最多再等 2 秒就强制收尾（Go 1.20+）
    out, err := cmd.CombinedOutput()

    if ctx.Err() != nil {
        return "", ctx.Err() // 父 ctx 被取消（用户中断），原样往上返回
    }
    if errors.Is(toolCtx.Err(), context.DeadlineExceeded) {
        return "", fmt.Errorf("command timed out after %s", bashTimeout) // 单个工具超时，交给模型
    }
    if err != nil {
        return "", fmt.Errorf("%w\n%s", err, out) // 把命令输出一并带上，模型才知道错在哪
    }
    return string(out), nil
}
```

注意这里**先检查父 ctx，再检查子 ctx**：两者都可能导致命令被杀掉，只有先检查父 ctx，才能分清"用户中断"（往上返回）和"单个工具超时"（交给模型）。

> 这个版本用来说明 ctx 的用法，还不够安全：`bash` 在后台启动的子进程（如 `npm run dev &`）在超时后会继续运行，输出大小也没有限制。完整版见第 13 节。

**发 HTTP 请求：`http.NewRequestWithContext`**

```go
const maxFetchBytes = 100_000

func fetchURL(ctx context.Context, input json.RawMessage) (string, error) {
    var in struct {
        URL string `json:"url"`
    }
    if err := json.Unmarshal(input, &in); err != nil {
        return "", fmt.Errorf("invalid input: %w", err)
    }

    req, err := http.NewRequestWithContext(ctx, http.MethodGet, in.URL, nil)
    if err != nil {
        return "", err
    }
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return "", err
    }
    defer resp.Body.Close()

    body, err := io.ReadAll(io.LimitReader(resp.Body, maxFetchBytes)) // 限制大小，别把整个网页塞进上下文
    return string(body), err
}
```

**自己写的长耗时逻辑：在循环里检查 `ctx.Done()`**

```go
for _, item := range items {
    select {
    case <-ctx.Done():
        return "", ctx.Err()
    default:
    }
    process(item)
}
```

### 6.4 坑：中断后 tool_use 没有配对的 tool_result

如果某个工具执行到一半被中断，`messages` 里最后一条 assistant 消息会带着 `tool_use`，后面却没有对应的 `tool_result`。如果要保存对话历史、下次接着跑，API 会因为缺少 `tool_result` 返回 400。

解决办法：中断时，给每个没执行完的 `tool_use` 补一条 `is_error` 的结果（比如内容写"用户中断"），再保存历史。如果只是退出程序、不恢复对话，可以不用管。

### 6.5 安全提醒

`bash` 工具会执行模型给出的任意命令。学习阶段至少要做到下面一条：

- 执行前打印命令，在终端里确认（y/n）才执行。确认逻辑放在 `callTool` 里、调用 `fn(ctx, input)` 之前，这就是一个最简单的 **PreToolUse 钩子**（02 的主题）
- 或者用一个限制了权限的工作目录、容器来跑

## 7. ctx 与 SDK 自带超时、重试的关系

| 机制 | 默认值 | 管的范围 | 配置方式 |
|---|---|---|---|
| SDK 单次请求超时 | 10 分钟 | 单次 HTTP 请求 | `option.WithRequestTimeout(time.Duration)` |
| SDK 自动重试 | 2 次（429、5xx、连接错误） | 失败后再发 | `option.WithMaxRetries(n)` |
| ctx 截止时间 / 取消 | 无（`Background()`） | **整个调用的总时长，包括所有重试** | `context.WithTimeout` / `NotifyContext` |

- ctx 一到期或被取消，重试也会跟着停
- 只想调单次请求的超时，用 `option.WithRequestTimeout`；想限制总时长或支持中途取消，用 ctx

## 8. 最佳实践与常见坑清单

### 最佳实践

- [ ] 在 `main` 里用 `signal.NotifyContext` 创建根 ctx，`defer stop()`
- [ ] ctx 作为**第一个参数**，一路往下传：`agentLoop → Messages.New / runTools → 工具`
- [ ] 下层需要超时时，**从传进来的 ctx 派生**（`context.WithTimeout(ctx, ...)`），不要新建 `Background()`
- [ ] `WithTimeout` / `WithCancel` 之后立刻 `defer cancel()`
- [ ] 错误往上返回时用 `%w` 包装，上层用 `errors.Is(err, context.Canceled)` 判断
- [ ] 工具内部用 `exec.CommandContext`、`http.NewRequestWithContext` 这类支持 ctx 的 API
- [ ] 区分"工具失败"（`is_error` 交给模型）和"用户中断"（终止循环）
- [ ] 长循环里 `select` 检查 `ctx.Done()`

### 常见坑

| 坑 | 现象 | 修正 |
|---|---|---|
| 下层写了 `context.Background()` | 按 Ctrl+C 后这一层还在跑 | 改成从参数 ctx 派生 |
| 忘了 `defer cancel()` | 资源泄漏，`go vet` 报警告 | `WithTimeout` 下一行就写 `defer cancel()` |
| 错误用 `%v` 包装 | `errors.Is(err, context.Canceled)` 永远为 false | 改用 `%w` |
| 把 ctx 存进结构体 | 生命周期混乱，取消行为不可预测 | 每次方法调用时传 ctx |
| 收到信号后不调用 `stop()` | 收尾卡住时，第二次 Ctrl+C 也没反应 | `<-ctx.Done()` 之后调用 `stop()` |
| 把 `context.Canceled` 当成工具失败交给模型 | 用户中断了，模型却还在继续重试 | `runTools` 里单独判断，直接往上返回 |
| 中断后直接保存历史 | 下次恢复时 API 返回 400（缺 `tool_result`） | 给未完成的 `tool_use` 补 `is_error` 结果 |
| `exec.Command` 没带 ctx | 按 Ctrl+C 后子进程变成孤儿进程继续运行 | 改用 `exec.CommandContext`，并设置 `WaitDelay` |
| 只用了 `exec.CommandContext` | `bash` 被杀了，但它在后台启动的进程继续运行 | 设置进程组，取消时杀掉整个组（见第 13.2 节） |

## 9. history 的类型：MessageParam 与 Message

对话历史要用 **`[]anthropic.MessageParam`**，不是 `[]anthropic.Message`，也不要用 `[]any`。

```go
var history []anthropic.MessageParam
```

### 9.1 三个名字很像的类型

| 类型 | 是什么 | 对应 Python |
|---|---|---|
| `anthropic.MessageNewParams` | **整个请求**：model、max_tokens、system、messages、tools…… | `client.messages.create(**kwargs)` 的全部参数 |
| `anthropic.MessageParam` | **history 里的一条消息**：role + content | `{"role": "user", "content": ...}` 这个 dict |
| `anthropic.Message` | **API 返回的一条响应**：id、content、stop_reason、usage…… | `client.messages.create()` 的返回值 |

关系：history 是 `[]MessageParam`（单数的 Param，一条一条），放进 `MessageNewParams.Messages` 字段里发出去；API 返回 `*Message`，再用 `ToParam()` 转回 `MessageParam` 追加进 history。

```
                 MessageNewParams{ Messages: history }
history ──────────────────────────────────────────────▶ client.Messages.New
[]MessageParam                                                │
    ▲                                                         │ 返回 *Message
    │                 resp.ToParam()                          │
    └─────────────────────────────────────────────────────────┘
```

`Message` 上有 `id`、`stop_reason`、`usage` 这些只在响应里出现的字段，请求里不需要，所以两边是分开的类型。

### 9.2 命名规则：`Param` = 发出去的数据

这是 SDK 代码生成器（Stainless）的统一命名规则，不只是消息，所有类型都这样：

| | 含义 | 例子 |
|---|---|---|
| **带 `Param` 后缀** | 你要**发给** API 的输入 | `MessageParam`、`TextBlockParam`、`ToolParam`、`ToolResultBlockParam` |
| **不带后缀** | API **返回**给你的输出 | `Message`、`TextBlock`、`ToolUseBlock` |

用这个规则来看，"从用户输入构建一条消息"其实也是在准备**要发出去的数据**，所以它是 `Param`。history 本质上就是"下一次请求的输入"。

输入和输出分成两套类型，是因为字段要求不一样：

- **输出类型**：每个字段都一定有值，还带着原始 JSON 的元数据（`resp.JSON.xxx.Raw()` 就是这么来的）
- **输入类型**：大多数字段是可选的，要区分"没设置"和"零值"，所以有 `anthropic.String(...)`、`param.Opt` 这类包装

### 9.3 往 history 里加消息

| 消息来源 | 写法 | 说明 |
|---|---|---|
| 用户输入 | `anthropic.NewUserMessage(anthropic.NewTextBlock(userInput))` | |
| 模型回复 | `resp.ToParam()` | 把整条响应 `Message` 转成 `MessageParam` |
| 工具结果 | `anthropic.NewUserMessage(toolResults...)` | `toolResults` 是 `[]anthropic.ContentBlockParamUnion`，所有结果放进同一条 user 消息 |

```go
var history []anthropic.MessageParam

history = append(history, anthropic.NewUserMessage(anthropic.NewTextBlock("当前目录有什么文件？")))

for {
    resp, err := client.Messages.New(ctx, anthropic.MessageNewParams{
        Model: "claude-opus-5-5", MaxTokens: 16000, Messages: history,
    })
    if err != nil {
        return fmt.Errorf("messages.new: %w", err)
    }
    history = append(history, resp.ToParam()) // assistant 回复

    if resp.StopReason != anthropic.StopReasonToolUse {
        return nil
    }
    toolResults, err := runTools(ctx, resp)
    if err != nil {
        return err
    }
    history = append(history, anthropic.NewUserMessage(toolResults...)) // 工具结果
}
```

> **模型回复一定要用 `resp.ToParam()` 整条放回去**，不要只取出文字再自己拼一条 assistant 消息。回复里的 `tool_use`、`thinking` 块都要原样带回，否则下一轮模型找不到自己发起的工具调用，API 会返回 400。

### 9.4 相关类型

| 类型 | 说明 |
|---|---|
| `anthropic.ContentBlockParamUnion` | 请求里一个内容块的类型：text、tool_result、image 等 |
| `anthropic.ContentBlockUnion` | 响应里一个内容块的类型，用 `AsAny()` 区分具体是哪种 |
| `anthropic.BetaMessageParam` | 走 beta 接口（`client.Beta.Messages.New`，比如 tool runner、compaction）时用的版本，和非 beta 的类型**不能混用** |

### 9.5 和 Python 的对比

| | Python | Go |
|---|---|---|
| **构建要发送的消息** | 写 dict 就行，很简单 | 要记住一堆 `NewXxx` 函数和 `XxxParam` 类型，更繁琐 |
| **把响应放回 history** | `{"role": "assistant", "content": response.content}`，SDK 对象可以直接放回去发送 | `resp.ToParam()` 一步完成，编译器帮你检查类型 |
| **保存 history 到文件** | SDK 对象不能直接 `json.dumps`，要先 `.model_dump()`，容易出错 | `MessageParam` 是普通 struct，可以直接 `json.Marshal` |
| **出错时机** | 字段名、结构写错，运行时 API 才返回 400 | 大部分结构错误在编译时就暴露 |

总结：Go 构建消息时更繁琐，但把响应放回 history 这一步更安全。

### 9.6 觉得名字别扭？

可以在自己的代码里起个类型别名：

```go
type Turn = anthropic.MessageParam // 别名，和原类型完全等价，可以直接传给 SDK

var history []Turn
```

不过更建议直接用 `MessageParam`：别人读代码、或者对照 SDK 文档时，不用再多转换一层。记住"`Param` = 发出去的数据"这条规则，名字就不会混了。

### 9.7 history 放在哪里

- 只在一次 `agentLoop` 里用：写成函数里的局部变量
- 要在多轮用户输入之间保留对话：让 `main` 持有它，每次传进 `agentLoop`；或者让 `agentLoop` 返回更新后的 history；或者放进 `Agent` 结构体
- 一般不需要写成包级变量

## 10. 多返回值与包级初始化：以 os.Getwd() 构建 system prompt 为例

场景：想在 system prompt 里写上当前工作目录。Python 里一行就够了：

```python
SYSTEM = f"You're a coding agent in {os.getcwd()}. Use bash to solve tasks."
```

照搬到 Go 会撞上两个问题：

```go
const SYSTEM_PROMPT = "You're a coding agent of " + os.Getwd() + ", ..." // 编译错误
```

1. `os.Getwd()` 返回 `(string, error)` 两个值，不能直接放进表达式
2. `const` 里不能调用函数

### 10.1 多返回值必须先拆开

Go 没有异常，错误就是一个普通的返回值。函数返回两个值时，不能把它直接塞进表达式里：

```go
prompt := "cwd: " + os.Getwd() // 编译错误：multiple-value os.Getwd() (value of type (dir string, err error)) in single-value context
```

必须先接收，再判断：

```go
cwd, err := os.Getwd()
if err != nil {
    return fmt.Errorf("get cwd: %w", err)
}
prompt := "You're a coding agent in " + cwd
```

> 也可以用 `_` 丢掉 err：`cwd, _ := os.Getwd()`。但这样出错时 `cwd` 是空字符串，程序会悄悄带着错误的 prompt 继续跑。**不推荐。**

### 10.2 函数外能写什么

**函数外只允许出现声明，不能写流程控制。**

| 位置 | 允许 | 不允许 |
|---|---|---|
| 函数外（包级别） | `package`、`import`、`var`、`const`、`type`、`func` 声明 | `if`、`for`、`switch`、`:=`、单独的函数调用语句 |
| 函数内 | 都可以 | — |

原因：Go 规定函数外的每条声明都必须以关键字开头，解析器看第一个词就能知道这是哪种声明。这也是包级别不能用 `:=` 的原因，要写成 `var x = ...`（同样能推断类型）。

**`const` 的额外限制**：值必须在**编译期**就能算出来，比如字面量、其他常量、`len("abc")` 这类内建运算。**不能调用任何函数**，`os.Getwd()` 这种运行时才知道结果的就更不行了。

| | `const` | `var` |
|---|---|---|
| 值什么时候确定 | 编译期 | 运行时（包初始化时，早于 `main`） |
| 能否调用函数 | 不能 | 能，但函数只能返回**一个**值 |

### 10.3 推荐写法：在函数里构建，由 main 调用

```go
const systemPromptTemplate = "You're a coding agent in %s. Use bash to solve tasks. Act, don't explain."

func buildSystemPrompt() (string, error) {
    cwd, err := os.Getwd()
    if err != nil {
        return "", fmt.Errorf("get working directory: %w", err)
    }
    return fmt.Sprintf(systemPromptTemplate, cwd), nil
}

func main() {
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
    defer stop()

    systemPrompt, err := buildSystemPrompt()
    if err != nil {
        log.Fatal(err)
    }
    // 把 systemPrompt 传给 agentLoop
}
```

在 `agentLoop` 里使用（`System` 字段的类型是 `[]anthropic.TextBlockParam`，不是 `string`）：

```go
System: []anthropic.TextBlockParam{{Text: systemPrompt}},
```

好处：

- 出错能明确处理，可以返回给调用方，也可以打印友好提示
- 什么时候初始化由你控制，不会出现"环境变量还没加载就先读了"这种初始化顺序问题
- 依赖关系一目了然：`agentLoop` 需要 system prompt，就通过参数传进去

> 不变的部分（模板）用 `const`，运行时才知道的部分（cwd）在函数里算。

### 10.4 非要做成包级变量的话

**方式 A：`init()` 函数**。它在 `main` 之前自动执行，里面可以写任何流程控制：

```go
var systemPrompt string

func init() {
    cwd, err := os.Getwd()
    if err != nil {
        log.Fatalf("get working directory: %v", err)
    }
    systemPrompt = fmt.Sprintf(systemPromptTemplate, cwd)
}
```

**方式 B：用一个 `mustXxx` 函数给 `var` 赋初值**。`var` 的初值可以是函数调用，只要这个函数只返回一个值：

```go
var systemPrompt = mustSystemPrompt()

func mustSystemPrompt() string {
    cwd, err := os.Getwd()
    if err != nil {
        panic(fmt.Sprintf("get working directory: %v", err))
    }
    return fmt.Sprintf(systemPromptTemplate, cwd)
}
```

`mustXxx` 是 Go 的命名惯例，表示**出错就 panic**。标准库里也有，比如 `regexp.MustCompile`、`template.Must`。

**这两种方式的共同缺点：**

- 出错时只能 `log.Fatal` 或 `panic`，不能把错误交给调用方处理
- 在 `main` 之前就执行了。如果 `main` 里才用 `godotenv.Load()` 之类加载配置，这时还读不到
- 写测试时不好替换

所以 **10.3（在 `main` 里调用函数）是首选**。`init()` 和 `must` 只用在配置固定、启动时出错就该直接退出的场景。

### 10.5 包初始化顺序

```
1. 导入的包先初始化（递归）
2. 本包的包级 var 按依赖顺序初始化   ← var x = f() 在这里执行
3. 本包的 init() 函数按出现顺序执行   ← 一个文件里可以有多个 init
4. main()
```

### 10.6 和 Python 的对比

| | Python | Go |
|---|---|---|
| 出错方式 | 抛异常，可以不管，让它往上冒 | 作为返回值给你，必须显式接收 |
| 多返回值 | 返回 tuple，可以整体当一个值用 | 多个独立的值，不能直接放进表达式 |
| 模块顶层 | 可以写任意语句：`if`、`for`、函数调用 | 只能写声明；要执行代码就用 `init()` 或 `var x = f()` |
| 常量 | 没有真正的常量，只是约定（全大写） | `const` 必须是编译期就能确定的值 |
| 命名风格 | 常量用 `SYSTEM_PROMPT` | 用驼峰：`systemPrompt`（包内）/ `SystemPrompt`（导出）；大写开头表示导出，不表示常量 |

Go 这样写确实更啰嗦，但每个可能出错的地方在代码里都看得见，不会有"某个函数悄悄抛了个异常"这种情况。

## 11. 定义工具：ToolUnionParam 与 ToolParam

`MessageNewParams.Tools` 字段的类型是 `[]anthropic.ToolUnionParam`。

> 本节内容对照 SDK v2.4.0 源码（`message.go`）整理，示例代码均编译运行过。

### 11.1 `ToolUnionParam` 是什么：Go 里的"联合类型"

API 的 `tools` 数组里可以放好几种工具：你自己定义的工具、Anthropic 内置的 bash、web search、code execution 等等，每种的 JSON 结构都不一样。Go 没有联合类型（Python 里的 `A | B`），SDK 就用**一个结构体，每种可能的类型对应一个指针字段**来模拟：

```go
type ToolUnionParam struct {
    OfTool                      *ToolParam                      // 你自己定义的工具（最常用）
    OfBashTool20250124          *ToolBash20250124Param          // Anthropic 内置的 bash
    OfTextEditor20250728        *ToolTextEditor20250728Param
    OfWebSearchTool20260209     *WebSearchTool20260209Param     // 服务端执行的 web search
    OfCodeExecutionTool20260120 *CodeExecutionTool20260120Param
    // ... 一共二十多种
    paramUnion
}
```

**规则：只给其中一个字段赋值，其余保持 nil。** 序列化时，SDK 只输出不是 nil 的那个字段的内容。字段带了 `inline` 标签，所以 JSON 里不会出现 `OfTool` 这一层。

**为什么是指针？** 指针的 nil 可以明确表示"没选这一项"。结构体的零值做不到这一点，SDK 分不清"没设置"和"设置了一个空工具"。

> SDK 里带 `Union` 的类型都是"多选一"的设计：
> - **请求类型**（`XxxUnionParam`）：给一个 `OfXxx` 指针字段赋值
> - **响应类型**（`XxxUnion`，如 `ContentBlockUnion`）：用 `AsAny()` 做类型分支

### 11.2 自定义工具：`ToolParam`

```go
var bashTool = anthropic.ToolParam{
    Name:        "bash",
    Description: anthropic.String("Run a shell command in the current working directory and return its combined stdout/stderr."),
    InputSchema: anthropic.ToolInputSchemaParam{
        Properties: map[string]any{
            "command": map[string]any{
                "type":        "string",
                "description": "The shell command to run",
            },
        },
        Required: []string{"command"},
    },
}

var tools = []anthropic.ToolUnionParam{
    {OfTool: &bashTool}, // 取地址，放进对应的指针字段
}
```

在请求里使用：

```go
resp, err := client.Messages.New(ctx, anthropic.MessageNewParams{
    Model:     "claude-opus-5-5",
    MaxTokens: 16000,
    System:    []anthropic.TextBlockParam{{Text: systemPrompt}},
    Messages:  history,
    Tools:     tools,
})
```

**`ToolParam` 的常用字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `Name` | `string` | **必填**。模型调用时用的名字，要和代码里分发工具用的 key 一致 |
| `InputSchema` | `ToolInputSchemaParam` | **必填**。描述输入参数的 JSON Schema |
| `Description` | `param.Opt[string]` | 强烈建议写。模型靠它判断什么时候用、怎么用这个工具。用 `anthropic.String(...)` 包装 |
| `Strict` | `param.Opt[bool]` | 设为 true 时，模型给出的输入保证符合 schema。用 `anthropic.Bool(true)` |
| `EagerInputStreaming` | `param.Opt[bool]` | 流式请求时让大段工具输入边生成边返回 |
| `CacheControl` | `CacheControlEphemeralParam` | 在这个工具处打缓存断点 |

**为什么 `Description` 要写成 `anthropic.String(...)`？** 它的类型是 `param.Opt[string]`，这是可选字段：要区分"没设置"（不输出这个字段）和"设成了空字符串"。这就是 [9.2 节](#92-命名规则param--发出去的数据) 说的，输入类型需要这种包装。`anthropic.String`、`anthropic.Bool`、`anthropic.Int` 就是用来构造它的。

**`ToolInputSchemaParam` 的字段：**

| 字段 | 说明 |
|---|---|
| `Properties` | 类型是 `any`，一般传 `map[string]any`，写法和 JSON Schema 一样 |
| `Required` | 必填参数的名字列表 |
| `Type` | 不用写，序列化时自动填 `"object"` |
| `ExtraFields` | 结构体没覆盖到的 schema 字段放这里，比如 `additionalProperties` |

### 11.3 开启 strict 模式

`strict: true` 要求 schema 里有 `additionalProperties: false`。`ToolInputSchemaParam` 没有这个字段，所以要放进 `ExtraFields`：

```go
var bashTool = anthropic.ToolParam{
    Name:        "bash",
    Description: anthropic.String("Run a shell command ..."),
    InputSchema: anthropic.ToolInputSchemaParam{
        Properties: map[string]any{
            "command": map[string]any{"type": "string", "description": "The shell command to run"},
        },
        Required:    []string{"command"},
        ExtraFields: map[string]any{"additionalProperties": false},
    },
    Strict: anthropic.Bool(true),
}
```

实际序列化出来的 JSON 是这样，`additionalProperties` 被合并进了 `input_schema`：

```json
{
  "name": "bash",
  "description": "Run a shell command ...",
  "strict": true,
  "input_schema": {
    "type": "object",
    "properties": { "command": { "type": "string", "description": "The shell command to run" } },
    "required": ["command"],
    "additionalProperties": false
  }
}
```

开了 strict，`runBash` 里 `json.Unmarshal` 拿到的输入就一定有 `command` 字段，也不会多出别的字段。

### 11.4 辅助函数：`ToolUnionParamOfTool`

SDK 提供了一个直接构造 union 的函数，只接收两个必填参数：

```go
readFileTool := anthropic.ToolUnionParamOfTool(
    anthropic.ToolInputSchemaParam{
        Properties: map[string]any{"path": map[string]any{"type": "string"}},
        Required:   []string{"path"},
    },
    "read_file",
)
```

它不能设置 `Description`、`Strict` 这些可选字段，所以实际用得不多。**更推荐 `{OfTool: &tool}` 的写法**，所有字段都能写全。

### 11.5 内置工具：选对应的 `Of*` 字段

Anthropic 定义好的工具不需要写 schema，结构体留空就行，`name` 和 `type` 会自动填上：

```go
tools := []anthropic.ToolUnionParam{
    {OfTool: &bashTool},                                                // 自定义工具：你执行
    {OfWebSearchTool20260209: &anthropic.WebSearchTool20260209Param{}}, // 服务端工具：Anthropic 执行
}
```

序列化出来是 `{"name": "web_search", "type": "web_search_20260209"}`。

| 类型 | 谁来执行 | 你要做什么 |
|---|---|---|
| 自定义工具（`OfTool`） | 你的程序 | 收到 `tool_use` 后自己执行，返回 `tool_result` |
| 内置的客户端工具（`OfBashTool20250124`、`OfTextEditor*`） | 你的程序 | schema 由 Anthropic 定义，执行还是你来做 |
| 服务端工具（`OfWebSearchTool*`、`OfCodeExecutionTool*`） | Anthropic 的服务器 | 什么都不用做，结果直接出现在回复里 |

> 你自己定义的、名叫 `"bash"` 的 `ToolParam`，和内置的 `OfBashTool20250124` 是**两种不同的工具**。从零写 agent 时用自定义的就好，schema 由你控制，更便于理解整个流程。

### 11.6 读取 union 里的内容：`GetXxx()` 方法

`ToolUnionParam` 上有一组 getter，不管里面是哪种工具，都能直接取出公共字段：

```go
for _, t := range tools {
    if name := t.GetName(); name != nil {
        fmt.Println(*name) // "bash"、"web_search"
    }
}
```

这些方法返回指针，那种工具没有这个字段时返回 nil，所以用之前要先判断。

### 11.7 定义和实现放在一起

工具的"定义"（发给模型的 schema）和"实现"（[6.1 节](#61-工具注册表每个工具都接收-ctx) `toolRegistry` 里的函数）如果分开写，名字要手动保持一致，很容易漏改。可以把它们放进同一个结构体：

```go
type Tool struct {
    Def anthropic.ToolParam // 发给模型的定义
    Run ToolFunc            // 收到调用时执行的函数
}

var allTools = []Tool{
    {Def: bashTool, Run: runBash},
}

// 发给 API 的工具列表
func toolParams(ts []Tool) []anthropic.ToolUnionParam {
    params := make([]anthropic.ToolUnionParam, len(ts))
    for i := range ts {
        params[i] = anthropic.ToolUnionParam{OfTool: &ts[i].Def}
    }
    return params
}

// 按名字分发用的注册表
func toolRegistryOf(ts []Tool) map[string]ToolFunc {
    registry := make(map[string]ToolFunc, len(ts))
    for _, t := range ts {
        registry[t.Def.Name] = t.Run
    }
    return registry
}
```

这样每个工具只在一个地方定义，名字也只有一个来源。以后加工具，在 `allTools` 里加一行就行。

这个结构也方便 02 的 PreToolUse：在 `Tool` 里再加一个字段，比如 `NeedsApproval bool`，就能按工具决定执行前要不要确认。

> `toolParams` 里写的是 `&ts[i].Def`（取切片元素的地址），不是先 `t := ts[i]` 再取 `&t.Def`。前者指向切片里的数据本身，不会多复制一份。

### 11.8 常见坑

| 坑 | 现象 | 修正 |
|---|---|---|
| 同时给两个 `Of*` 字段赋值 | 序列化出错或请求被拒 | 一个 `ToolUnionParam` 只设一个字段 |
| `Description: "..."` 直接写字符串 | 编译错误：类型是 `param.Opt[string]` | 写成 `anthropic.String("...")` |
| 开了 `Strict` 但没写 `additionalProperties: false` | API 返回 400 | 放进 `InputSchema.ExtraFields` |
| 定义里的 `Name` 和注册表的 key 不一致 | 模型调用了工具，你这边报 `unknown tool` | 用 11.7 节的写法，名字只定义一次 |
| 用 `tool_choice` 强制模型调用工具（`any` / `tool`） | Opus 5.5 上返回 400 | 用默认的 `auto`，在 system prompt 里说明什么时候该用哪个工具 |

## 12. 解析响应：判断 tool_use 与取出工具输入

`resp.Content` 是 `[]anthropic.ContentBlockUnion`，每个元素可能是 text、thinking、tool_use 等不同类型的块。本节解决两个问题：

1. 怎么判断一个块是不是 `tool_use`，不用手写 `"tool_use"` 字符串
2. 怎么取出 `tool_use` 输入里的具体字段，比如 bash 工具的 `command`

> 本节代码用一段模拟的 API 响应 JSON 在 SDK v2.4.0 上实际运行过。

### 12.1 判断块类型：用类型分支，不比较字符串

**推荐写法：`AsAny()` 加 type switch**

```go
for _, block := range resp.Content {
    switch b := block.AsAny().(type) {
    case anthropic.ToolUseBlock:
        // 这里 b 的类型已经是 ToolUseBlock，可以直接用 b.ID、b.Name、b.Input
    case anthropic.TextBlock:
        fmt.Println(b.Text)
    }
}
```

完全不用写 `"tool_use"` 字符串：判断依据是 **Go 的类型**，而不是 `Type` 字段的值。

| | 比较字符串 `block.Type == "tool_use"` | 类型分支 `case anthropic.ToolUseBlock` |
|---|---|---|
| 拼错时 | 静默不匹配，运行时才发现 | 编译报错 |
| 匹配后 | `block` 还是 union，要再转换 | `b` 直接就是 `ToolUseBlock`，字段都能用 |
| 编辑器支持 | 无 | 补全、跳转定义 |

**只关心一种类型时：用类型断言**

```go
use, ok := block.AsAny().(anthropic.ToolUseBlock)
if !ok {
    continue
}
```

**`As` 系列方法**

`ContentBlockUnion` 上还有 `AsToolUse()`、`AsText()`、`AsThinking()` 等方法，直接返回对应的具体类型。但它们**不检查实际类型**：块明明是 text，调用 `AsToolUse()` 也会返回一个字段全是零值的 `ToolUseBlock`。所以要先确认类型再用，一般不如 `AsAny()` 加类型分支方便。

### 12.2 SDK 里的常量

`ToolUseBlock` 的 `Type` 字段类型是 `constant.ToolUse`，值永远是 `"tool_use"`（定义在 `shared/constant/constants.go`）。真要比较字符串，可以这样写：

```go
import "github.com/anthropics/anthropic-sdk-go/v2/shared/constant"

var tu constant.ToolUse
if block.Type == string(tu.Default()) { ... } // 能用，但比直接写 "tool_use" 还难读
```

SDK 生成这些常量类型，主要是为了**序列化时自动填对 `type` 字段**，不是给你拿来比较的。所以判断块类型时**用 12.1 的类型分支**。

**`StopReason` 有现成的常量**，可以直接比较：

| 常量 | 值 | 含义 |
|---|---|---|
| `anthropic.StopReasonEndTurn` | `"end_turn"` | 模型说完了 |
| `anthropic.StopReasonToolUse` | `"tool_use"` | 模型要调用工具，等你返回结果 |
| `anthropic.StopReasonMaxTokens` | `"max_tokens"` | 达到 `MaxTokens` 上限，回复被截断 |
| `anthropic.StopReasonRefusal` | `"refusal"` | 被安全分类器拒绝 |

```go
if resp.StopReason != anthropic.StopReasonToolUse {
    return nil
}
```

### 12.3 取出工具输入：`json.Unmarshal` 到结构体

`ToolUseBlock` 的定义（SDK 源码，有删节）：

```go
type ToolUseBlock struct {
    ID    string           // tool_use_id，回传 tool_result 时要用
    Input json.RawMessage  // 原始 JSON，比如 {"command": "ls -la"}
    Name  string           // 工具名，比如 "bash"
    Type  constant.ToolUse // 永远是 "tool_use"
    ...
}
```

`Input` 是 `json.RawMessage`，也就是**还没解析的原始 JSON 字节**。定义一个结构体，用 `json.Unmarshal` 解析：

```go
type BashInput struct {
    Command string `json:"command"` // tag 要和工具 schema 里的字段名一致
}

for _, block := range resp.Content {
    use, ok := block.AsAny().(anthropic.ToolUseBlock)
    if !ok {
        continue
    }

    var in BashInput
    if err := json.Unmarshal(use.Input, &in); err != nil {
        // 解析失败时作为 is_error 结果交给模型，不要让程序崩溃
        results = append(results, anthropic.NewToolResultBlock(use.ID, "invalid input: "+err.Error(), true))
        continue
    }
    fmt.Println(in.Command) // "ls -la"
}
```

对一段模拟的响应实际运行，输出是：

```
name=bash id=toolu_1 command="ls -la"
```

### 12.4 为什么用结构体，不用 `map[string]any`

```go
// 用 map：每次取值都要做类型断言
var m map[string]any
json.Unmarshal(use.Input, &m)
cmd, ok := m["command"].(string) // 字段名写错时，只会悄悄得到 ok == false

// 用结构体：字段和类型一目了然
var in BashInput
json.Unmarshal(use.Input, &in)
cmd := in.Command
```

结构体的字段和你在 `ToolParam.InputSchema` 里写的 schema 一一对应，读代码时也能一眼看出这个工具接收什么参数。

### 12.5 两种拿到原始 JSON 的方式

| 写法 | 类型 | 说明 |
|---|---|---|
| `use.Input` | `json.RawMessage` | **推荐**，直接传给 `json.Unmarshal` |
| `use.JSON.Input.Raw()` | `string` | 响应元数据里保存的原始 JSON，要转成 `[]byte` 才能 `Unmarshal` |

两种拿到的是同一份 JSON，实际运行结果一致。`Input` 本身就是 `json.RawMessage`，所以直接用它更简单。第 6.2 节 `runTools` 里也是这么写的。

### 12.6 常见坑

| 坑 | 现象 | 修正 |
|---|---|---|
| 结构体字段小写开头，如 `command string` | `json.Unmarshal` 不报错，但字段一直是空字符串 | 字段名大写开头（`Command`），JSON 名字用 tag 指定：`` `json:"command"` `` |
| tag 和 schema 里的字段名不一致 | 同上，字段一直是空值 | tag 和 `InputSchema.Properties` 的 key 保持一致 |
| 对 text 块调用 `AsToolUse()` | 拿到一个全是零值的 `ToolUseBlock`，没有任何报错 | 用 `AsAny()` 加类型分支，先确认类型 |
| 输入解析失败时直接 `log.Fatal` | 模型一次给错参数，整个 agent 就退出了 | 作为 `is_error` 的 `tool_result` 交给模型，让它修正后重试 |
| 字符串匹配原始 JSON，比如 `strings.Contains(string(use.Input), "rm")` | 模型的 JSON 转义方式可能不同（Unicode、`\/`），匹配不可靠 | 先 `json.Unmarshal`，再检查解析出来的字段 |

## 13. 安全地执行 bash 命令：子进程、goroutine 与防护

### 13.1 先分清：子进程和 goroutine

| | 是什么 | 用来做什么 |
|---|---|---|
| **子进程**（`os/exec`） | 操作系统里一个独立的进程，这里就是 `bash` | 真正执行命令 |
| **goroutine**（`go func()`） | Go 运行时管理的轻量级线程 | 让等待命令执行的过程不阻塞别的事，或者同时跑好几个命令 |

单个命令按顺序执行时，**不需要 goroutine**：`cmd.Run()` 会阻塞到命令结束，这在 agent loop 里正好合适，因为模型本来就要等结果。需要 goroutine 的场景是：模型在一次回复里发起了好几个工具调用，你想并行执行它们（第 13.4 节）。

安全执行分三层：

| 层 | 解决的问题 | 小节 |
|---|---|---|
| 子进程 | 命令执行不出问题：不卡死、不留后台进程、输出不爆上下文 | 13.2、13.3 |
| goroutine | 并行执行时不出数据竞争，一个工具失败不影响别的 | 13.4 |
| 防护 | 不执行不该执行的命令，不泄漏 API key | 13.5 |

### 13.2 第 1 层：子进程本身要安全

完整实现（适用于 macOS 和 Linux）：

```go
const (
    bashTimeout    = 30 * time.Second
    maxOutputBytes = 30_000
    waitDelay      = 2 * time.Second
)

func runCommand(ctx context.Context, workDir, command string) (string, error) {
    // ① 单个命令的超时，从父 ctx 派生，所以 Ctrl+C 也能传下来
    toolCtx, cancel := context.WithTimeout(ctx, bashTimeout)
    defer cancel()

    cmd := exec.CommandContext(toolCtx, "bash", "-c", command)

    // ② 固定工作目录
    cmd.Dir = workDir

    // ③ 只传必要的环境变量，不把 API key 交给子进程（见 13.5）
    cmd.Env = safeEnv()

    // ④ 让 bash 自成一个进程组，取消时杀掉整个组（包括它启动的所有子进程）
    cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}
    cmd.Cancel = func() error {
        return syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL) // 负的 PID 表示整个进程组
    }

    // ⑤ 杀掉之后最多再等 2 秒，防止 Wait 被残留的输出管道卡住
    cmd.WaitDelay = waitDelay

    // ⑥ 限制输出大小
    out := &limitedBuffer{limit: maxOutputBytes}
    cmd.Stdout = out
    cmd.Stderr = out
    // ⑦ cmd.Stdin 不设置，就会连到空设备：需要交互输入的命令读到 EOF 后直接结束，不会一直挂着

    err := cmd.Run()
    if ctx.Err() != nil {
        return "", ctx.Err() // 用户中断：原样往上返回
    }
    if errors.Is(toolCtx.Err(), context.DeadlineExceeded) {
        return out.String(), fmt.Errorf("command timed out after %s", bashTimeout)
    }
    if err != nil {
        return out.String(), fmt.Errorf("command failed: %w", err) // 非 0 退出码等，输出一并带上
    }
    return out.String(), nil
}
```

限制输出大小的 writer：

```go
type limitedBuffer struct {
    mu        sync.Mutex
    buf       strings.Builder
    limit     int
    truncated bool
}

func (b *limitedBuffer) Write(p []byte) (int, error) {
    b.mu.Lock()
    defer b.mu.Unlock()
    remaining := b.limit - b.buf.Len()
    if remaining <= 0 {
        b.truncated = true
        return len(p), nil // 超出部分丢掉，但要返回 len(p)，否则命令会因为写失败而出错
    }
    if len(p) > remaining {
        b.buf.Write(p[:remaining])
        b.truncated = true
        return len(p), nil
    }
    b.buf.Write(p)
    return len(p), nil
}

func (b *limitedBuffer) String() string {
    b.mu.Lock()
    defer b.mu.Unlock()
    if b.truncated {
        return b.buf.String() + fmt.Sprintf("\n...[output truncated at %d bytes]", b.limit)
    }
    return b.buf.String()
}
```

stdout 和 stderr 写进同一个 `limitedBuffer`，可能被同时写入，所以要加 `sync.Mutex`。

### 13.3 为什么每一步都需要

**④ 进程组最容易被忽略。** 对照实验：

| 写法 | 命令 `(sleep 3; echo SURVIVED > 文件) & sleep 100`，1 秒超时 |
|---|---|
| 只用 `exec.CommandContext` | `Run` 在 1 秒后返回 `signal: killed`，**但后台的孙子进程活了下来，3 秒后照样写了文件** |
| 加上进程组和 `cmd.Cancel` | 孙子进程一起被杀掉，没有写文件 |

原因：`CommandContext` 默认只杀它直接启动的那个进程，也就是 `bash`。bash 启动的子进程会变成孤儿进程，继续在后台运行。模型很容易写出 `npm run dev &`、`python server.py &` 这种命令，不杀整个进程组，就会越积越多。

其他几步：

| 步骤 | 不做会怎样 |
|---|---|
| ① 超时 | `sleep 999`、`tail -f` 这种命令永远不结束，agent 卡死 |
| ② 工作目录 | 命令在哪个目录运行取决于你从哪里启动程序，结果不可预期 |
| ③ 环境变量 | 模型执行 `env`，你的 API key 就出现在输出里，还会被发回 API |
| ⑤ `WaitDelay` | 孙子进程还拿着输出管道时，`Wait` 可能一直等下去 |
| ⑥ 限制输出 | `cat` 一个大文件，几 MB 输出全塞进上下文，既耗 token 又可能超出上下文长度 |
| ⑦ 不接 stdin | 如果把 stdin 接到你的终端，需要输入的命令（如 `git commit` 打开编辑器）会和你的 REPL 提示符抢输入 |

在 macOS 上的测试结果：

```
timeout test:    err=command timed out after 2s elapsed=2s
truncation test: len=1036 tail="y\ny\n\n...[output truncated at 1000 bytes]"
cancel test:     err=context canceled isCanceled=true
grandchild test: killed (no marker file)
```

> **跨平台**：`Setpgid` 和 `syscall.Kill` 只在 macOS 和 Linux 上有，在 Windows 上会编译失败。要跨平台的话，把这部分放进开头写着 `//go:build unix` 的文件，Windows 版另写一个文件。

### 13.4 第 2 层：用 goroutine 并行执行多个工具

模型一次回复里可能有好几个 `tool_use`。并行执行时用 **`errgroup`**（`golang.org/x/sync/errgroup`），不要自己写 `go func()` 加 `sync.WaitGroup`：

```go
const maxParallelTools = 4

func runToolsParallel(ctx context.Context, uses []anthropic.ToolUseBlock) ([]anthropic.ContentBlockParamUnion, error) {
    results := make([]anthropic.ContentBlockParamUnion, len(uses)) // 预先分配，每个 goroutine 只写自己的下标
    g, gctx := errgroup.WithContext(ctx)
    g.SetLimit(maxParallelTools) // 最多同时跑 4 个

    for i, use := range uses {
        g.Go(func() error {
            output, err := callTool(gctx, use.Name, use.Input)
            if errors.Is(err, context.Canceled) {
                return err // 只有用户中断才返回错误，这会取消其他所有 goroutine
            }
            if err != nil {
                results[i] = anthropic.NewToolResultBlock(use.ID, output+"\n"+err.Error(), true)
                return nil // 工具失败不返回错误，不影响其他工具
            }
            results[i] = anthropic.NewToolResultBlock(use.ID, output, false)
            return nil
        })
    }

    if err := g.Wait(); err != nil {
        return nil, err
    }
    return results, nil
}
```

测试结果（用 `go run -race` 运行，没有报数据竞争）：3 个命令 `sleep 1; echo a`、`echo b`、`echo oops >&2; exit 3` 总共用了 1 秒；结果顺序和输入一致，失败的那个以 `is_error: true` 返回，内容是 `"oops\n\ncommand failed: exit status 3"`，没有影响另外两个。

| 要点 | 说明 |
|---|---|
| **结果按下标写** | 预先分配 `results`，每个 goroutine 只写 `results[i]`。不同下标互不冲突，不需要加锁；也保证结果顺序和 `tool_use` 的顺序一致 |
| **不要在 goroutine 里 `append` 同一个切片** | 多个 goroutine 同时 `append` 是数据竞争，结果可能丢失或程序崩溃 |
| **想清楚 errgroup 的取消语义** | 任何一个 goroutine 返回非 nil 错误，`gctx` 就会被取消，其他 goroutine 的命令也会被杀掉。所以工具失败要返回 `nil`，只有用户中断才返回错误 |
| **一定要 `g.Wait()`** | 不等所有 goroutine 结束就返回，它们会继续在后台跑，结果也会丢失 |
| **限制并发数** | `g.SetLimit(n)`：模型一次发起十几个命令时，不会同时起十几个进程 |
| **循环变量** | Go 1.22 起每轮循环的 `i`、`use` 都是新变量，可以直接在闭包里用；Go 1.21 及以前必须先复制一份 |
| **用 `-race` 检查** | `go run -race` / `go test -race` 是 Go 自带的数据竞争检测，并发代码写完都应该跑一遍 |

> `golang.org/x/sync` 在 `go.mod` 里标的是 `indirect`。代码里用到它之后，运行一次 `go mod tidy`，它就会变成直接依赖。

**要不要并行？** 模型发起的多个工具调用之间可能有先后依赖（比如先 `mkdir` 再往里写文件），模型通常会分到不同轮次里，但不能保证。学习阶段顺序执行更简单，也更好调试；确认需要提速时再换成并行。

### 13.5 第 3 层：防止模型执行危险命令

前两层解决的是"命令执行不出问题"，这一层解决的是"不执行不该执行的命令"。模型给出的命令可能有误，也可能是读到的网页内容里藏了提示注入，诱导它执行恶意命令。

**1. 执行前确认**（这就是 02 要做的 PreToolUse）

```go
fmt.Printf("\n模型要执行：%s\n允许吗？[y/N] ", in.Command)
answer, _ := reader.ReadString('\n')
if strings.TrimSpace(strings.ToLower(answer)) != "y" {
    return "", errors.New("user denied this command")
}
```

这里的 `reader` 要和 REPL 用同一个 `bufio.Reader`，不要再新建一个：两个 `bufio.Reader` 读同一个 stdin，会互相抢走对方缓冲区里的输入。并行执行时，确认要放在启动 goroutine 之前逐个问，不然几个提示会同时打印出来。

**2. 别把你的 API key 交给子进程**

子进程默认继承你的所有环境变量。只传必要的：

```go
func safeEnv() []string {
    return []string{
        "PATH=" + os.Getenv("PATH"),
        "HOME=" + os.Getenv("HOME"),
        "LANG=" + os.Getenv("LANG"),
    }
}
```

测试：设置 `ANTHROPIC_API_KEY` 后执行 `echo "key=[$ANTHROPIC_API_KEY]"`，输出是 `key=[]`。

**3. 更严格的隔离**：在 Docker 容器里或者用一个权限受限的用户来运行。学习阶段至少做到第 1、2 条。
